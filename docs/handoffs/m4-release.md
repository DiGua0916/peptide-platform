# M4 发布说明（给 F1，2026-11-14 更新）

一句话：**M4 上线后，顾客、店员看到的东西一点不变，和线上已有功能重叠的部分也一样**。M4 自己写的东西都在开关后面，开关都关着。这一版不带 bug 修复：离开挽回统计表的问题用的是线上已有的修法。

**例外一处（11-14 复查时发现，发布前要定）**：线上投手首页的代码（`admin/class-buyer-home.php`，不归 F2）只要发现 M4 的 `Pricing\Campaigns::running()` 存在，就显示“当前在跑的活动”卡片。所以 M4 一上线，投手账号的首页会多出这张卡片。本机实测过：同一份数据，线上代码没有这张卡片，换成 M4 后卡片里列出 7 个活动。M4 自己的文件里关不住它，见第 2 节第 16 行和第 7 节。

## 0. 原则：和线上重叠的，以线上为准

平台所有者 2026-11-14 的原话：“以后遇上类似的问题，优先用站点已经存在的，因为那个是我亲自加的，而不是用你这块后面自己写的，你的是没经历过测试的”。

M4 怎么照这条做：

1. 凡是和线上已有功能重叠的地方（满减、优惠码、运费折扣、赠品 / 捆绑、积分券、首单优惠、离开挽回 / 转盘、活动倒计时、营销后台谁能看谁能改），**都按线上的行为来**。M4 的实现要么放在开关后面关着，要么不进包。
2. 同一个问题两边都修了的，用线上的修法，M4 那份删掉。离开挽回统计表就是这样处理的：用日常会话的 `f5a0b2d`，M4 自己的版本已经删掉。
3. 开关关着时，M4 在这些地方只多一个“开关开了没有”的判断。没开就走线上原来的代码，一行不差。M4 没有删掉线上的任何逻辑：改写的 25 行都是在原来的判断上加了条件，这些条件只在开关打开时才起作用。
4. 以后打开任何一个开关都算功能变化，要所有者先定。打开以后如果和线上的结果不一样，**以线上为准**：改 M4 去对齐线上，不改线上去迁就 M4。
5. “上线后看到的东西一点不变”这句话也包括重叠的部分。重叠的地方逐项列在第 2 节，比对和页面渲染的结果在第 3 节，和线上逐字节相同。唯一的例外是投手首页那张卡片（第 2 节第 16 行）。它是线上代码看到 M4 在场后自己显示出来的，M4 的文件里关不住。
6. 线上代码里凡是“M4 合进来就自动启用”的地方，也按重叠处理。主线 `24d1671` 里一共两处：营销菜单（结果不变）和投手首页的卡片（会变）。

## 3. 怎么确认“一点不变”（本机，2026-11-14）

比对方法：同一份数据库快照，站点先装线上代码（主线 `24d1671`）跑一遍 `tests/m4-release-compare-native.php`，再装 M4（`a226d0b`）跑一遍，比两份输出。比的内容：24 个购物车的每行单价、每张优惠码减了多少、被拒绝时的提示、满减费用、运费的每个选项和选中的那个、应付总额、满减进度条；前台的首单券条、离开挽回 / 转盘的配置、活动页、优惠码页、商品页上的满减；店铺后台的 10 个营销页面。

| 数据 | 线上代码 vs M4 |
| --- | --- |
| 干净的库 | 逐字节相同 |
| 像真实店铺的库（自己的满减三个、物流方案 $15 / $45、5 折运费折扣、首单券、离开挽回、赠品、统计表不在而版本号在） | 逐字节相同 |
| 同上，M4 的引擎开在影子档 | 逐字节相同 |
| 同上，M4 的引擎开在开档 | 逐字节相同 |
| 只用线上代码搭出来的库（升级路径的起点） | 逐字节相同 |

前台页面另外在命令行里渲染比对过（像真实店铺的库）：首页、商品列表、商品页、购物车用普通访客各渲染一次；首页、商品页再按“店铺打开了已购回访、访客带着已购 cookie”各渲染一次。每次渲染都会变的随机串（nonce、购物车令牌、时间戳）去掉，相关商品的随机排序用同一个种子固定之后，线上和 M4 **全部逐字节相同**。已购老顾客那一组，两边都有首单券条、都加载离开挽回脚本、都不输出静默脚本。也就是说已购回访的“静默”现在还不生效，和线上一样（见第 7 节第 1 条）。

投手首页也用投手账号渲染过（像真实店铺的库，`wp peptide buyer on` 开的投手）。这是**唯一不同的地方**：线上代码 3645 字节、没有活动卡片；M4 是 4455 字节，多了“当前在跑的活动”卡片（7 个活动）。原因见第 2 节第 16 行。

## 4. 升级和回退（本机走过）

起点是一份**只用线上代码**做出来的库：原始库 → 测试配送 → 运费 $15 → 店铺自己的满减、运费折扣、首单、弹窗、赠品 → 统计表不在而版本号在（就是五家子店当时的样子）→ 用 `wp peptide buyer on` 开一个投手。

| 步骤 | 结果 |
| --- | --- |
| 换成 M4 的代码，算一次购物车、打开后台营销页面、让弹窗弹出一次 | 购物车金额不变；三个开关的选项仍然不存在（也就是关着） |
| 比较升级前后的数据库 | 选项：没有新增、没有删除、没有值变了的（缓存类的不算）。表：多了一张 `pc_app_stats`，1 行（就是那次弹出）。**线上代码自己走同样的步骤，结果完全一样**（线上的 `f5a0b2d` 也会补建这张表），所以这不是 M4 带来的 |
| 投手账号 | 只读规则没生效，M4 不动投手的权限；营销页面仍由 M9 返回 403 |
| 换回线上代码（回退） | 输出和升级前一样。唯一的不同是离开挽回设置页的“弹出次数”从 0 变成 1，因为升级时那次弹出被记上了；线上代码自己走也是这样 |

**回退办法**：整个目录换回旧版就行，不用清选项，也不用动数据库。开关本来就关着，不用改。

## 7. 要所有者确认的

**发布前要定一件事：投手首页的“当前在跑的活动”卡片**（第 2 节第 16 行）。其余和线上重叠的地方都按线上来，不带 bug 修复，开关都关着。（生产上的操作照 F1 的规矩，要所有者同意后由 F1 执行。）

卡片的二选一：

- **甲（推荐，保持“一点不变”）**：`admin/class-buyer-home.php` 的负责人（F5 或日常会话）在 `render_campaigns()` 开头再加一个条件：当前用户有 `pc_view_campaigns` 才显示，例如 `if ( ! current_user_can( 'pc_view_campaigns' ) ) { return; }`。这样卡片和营销只读页同时出现，都等 M9 新版给投手角色加上这项权限。F2 不改别人的文件，也不改和 F5 定好的 `Campaigns::running()`。
- **乙**：所有者同意 M4 上线时投手首页就多出这张卡片。所有者 11-13 已经定过“投手可以看当前在跑的活动”，这张卡片只读，没有链接。

第 6 节的命令查出来 6 家店都没有投手账号的话，这张卡片暂时没人看得到，可以先发、再按甲处理。

## 8. 离“完全上线”还差什么

“完全上线”指价格引擎在 6 家店都开到 `on`，由引擎来算满减、赠品 / 捆绑和运费折扣。这是 M4 唯一会**替换**线上算法的地方，所以按第 0 节的原则：影子档期间顾客付的一直是线上算出来的钱，引擎只在一旁核对；核对的基准是线上的结果。

| # | 事情 | 谁 | 预计 |
| --- | --- | --- | --- |
| 1 | 在沙盒验证这一版（第 6 节），然后发布（开关都关着） | F1，排在 F4 之后 | F4 发完后 1 天 |
| 2 | 试点店 s0006 开影子档：`wp peptide price-engine mode shadow`。影子档不改任何价格，只在请求末尾再算一遍并核对 | F1（所有者确认） | 观察 2 天 |
| 3 | 其余 5 家开影子档 | F1 | 观察 5–7 天，要覆盖一个周末，至少碰上一次活动或优惠码的改动 |
| 4 | 每天看核对结果：`wp peptide price-engine status`（总后台的“价格引擎核对不一致”巡检在 F1 分支上，第 1 包发了以后才有） | F1 | 每天几分钟 |
| 5 | 试点店开 `on`：`wp peptide price-engine mode on`，和开之前同时段比订单数、客单价、支付成功率、报错 | F1（所有者确认） | 观察 2–3 天 |
| 6 | 其余 5 家开 `on` | F1（所有者确认） | — |

每次核对都比这 7 项金额：应付总额、商品小计、优惠码合计、每张优惠码、每个满减活动、运费、每行单价。

对不上时怎么办：

- 影子档里出现“不一致”或“出错”：把 `wp peptide price-engine log --limit=10` 的整行发给 F2。里面有购物车内容和两边的数字，没有顾客邮箱。F2 用它复现，加进对照样例，**改引擎去对齐线上的结果**（线上的算法不动），修好后随下一次发布上线。**不一致没清零之前不开 `on`。**
- “跳过”不算问题（比如购物车刚改完、还没重新计算的那一瞬间），但同一种跳过原因天天出现，要告诉 F2。
- 任何时候要停：`wp peptide price-engine mode off`；进不了后台时，在那家店的 `wp-config.php` 里加 `define( 'PC_PRICING_ENGINE_MODE', 'off' );`。不用回滚代码。

算下来，从 M4 发布到 6 家店都开到 `on`，顺利的话大约 **两周**（发布 1 天 + 影子档 7–9 天 + 开档 3–4 天）。中间如果出现要修的不一致，每修一次再加 2–3 天观察。

这两周之外、不算在“完全上线”里的：

- 营销弹窗静默（`pc_marketing_quiet_mode`）：等所有者决定要不要让已购回访的静默生效（第 7 节第 1 条）。
- 按系列接收营销活动（`pc_series_campaigns_mode`）：要等总后台的系列活动编辑界面做好、所有者决定。
- 投手只读页：跟 M9 新版一起上（F5 的分支要先合主线，现在和主线有 3 个它名下的文件冲突）。
- 总后台的三档开关页面还没有人负责；在那之前用命令行切。
- 浏览器走查（清单第 3 步）还没有人做过，建议在试点店影子期内用沙盒做一次。
- “下一个版本”的两件事（优惠码的四个检查改由引擎判定、删掉旧算法）：开到 `on` 并稳定以后再开始。删旧算法之前同样要所有者确认。

## 9. 统计表 6 家店都是 0 行（F1 11-14 问的，F2 查过）

结论：计数本身写得进去，0 行说明一直没有事件进来，最可能是弹窗从来没打开过。这件事和 M4 无关，M4 不改统计表的代码。

**F1 11-14 只读核对，已经结案：0 行是正常的。** 6 家店（s0001、s0006–s0010）都没有 `peptide_core_exit_intent` 这个选项，也就是从没配置过，等于关着；带 `_pc_exit_intent` 的订单都是 0；前台 nginx 访问日志（当前和上一份，共 4 个文件）里没有任何 `pc_exit_event` 请求。

查过的：

- 只有这几种情况会写一行：顾客看到弹窗（`show`）、点关闭（`close`）、领券（`claim`）、转盘（`spin` / `win`）、用弹窗给的券下单（`order`）。弹窗默认是关的（`enabled` 默认 `false`）；没在“应用中心 → 离开挽回”里打开过的店，什么都不会记。
- 员工不计数：登录着、有 `manage_woocommerce` 的账号（包括店主、总后台一键登录）看到弹窗不记，后台预览也不记。所以店主自己登录着测弹窗，表里不会有数字。
- 线上代码（主线 `24d1671`）在本机跑 `smoke-exit-intent` 37 / 0，“弹出计一次”“用弹窗券下单计一次、同一单不重复计”都通过。在“表不在、版本号在”的库上，第一次写入会自动建表再写（干净的库和这种库都跑过）。本机不能开网页端口，没有走真实的网页请求，用例是直接调用同一个处理函数。
- 五家子店的表是 11-13 17:50 UTC 才建的；就算这几家弹窗开着，也要在那之后才会开始有行。

请 F1 在一家店（建议主店，它的表一直都在）只读查下面三样，就能分清是哪种情况：

```bash
wp option get peptide_core_exit_intent --format=json
```

```bash
wp db query "SELECT COUNT(*) FROM $(wp db prefix)wc_orders_meta WHERE meta_key='_pc_exit_intent'"
```

```bash
grep -c 'wc-ajax=pc_exit_event' <这家店的 nginx 访问日志>
```

| 看到的 | 说明 |
| --- | --- |
| 第一条没有这个选项，或者 `"enabled":false` | 弹窗没开，0 行是正常的。要不要开由店主定 |
| `enabled` 是 `true`，第三条是 0 | 弹窗开着但从没弹出来过。看 `pages`（在哪些页面弹）、`audience`（`all` / `cart` / `new`）、`mobile`（手机端怎么触发，空 = 手机不弹）、`desktop_exit`。广告流量几乎都是手机 |
| 第三条有请求，但状态码不是 200 | 请求被拦了（斗篷或安全规则）。把那几行日志发给 F2 |
| 第三条有状态 200 的请求，表还是 0 行 | 这才是“计数写不进去”。把日志时间和 `wp db query "SHOW CREATE TABLE $(wp db prefix)pc_app_stats"` 的结果发给 F2 |

第二条是“用弹窗券下的单”数。它不是 0 而表是 0，也说明计数有问题。
