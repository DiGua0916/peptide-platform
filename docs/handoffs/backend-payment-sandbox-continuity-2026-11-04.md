# Payment-method switching and the sandbox cashier boundary

The owner reported an unconfirmed session followed by the earlier cross-method checkout error during a new PayPal sandbox test. They had already required that an old unpaid order remain available while a new checkout stays independent. This task resumes investigation of today's new checkout only; the owner stopped tracing the earlier reported transaction and this task does not reopen it.

Read-only production correlation established two separate causes. HQ had created today's redirect session, but its saved cashier host was `bestgoodsforyou.top`, while the account's frozen trust contained `sandbox.paypal.com` and `backupaoy.top`. The native URL policy rejected that result, so no usable URL reached the store. An upstream-created session is not evidence of a paid order. A returned URL alone does not authorize adding its host to trust; supplier confirmation has been requested. No new provider request or change to trust was made during diagnosis.

The same native pending order was then reused when the customer switched to the credit-card method. Woo saved the selected method before Gateway/Session_Service ran. The existing cross-method fence correctly refused a second payment on that old order, but the earlier checkout-navigation splitter required the current native method to still equal the frozen attempt method. That condition was now false, so even a new checkout GET could remain attached to the damaged draft. Independent source/model inspection reproduced this failure. Today's raw order remained pending, unpaid, with equal full and financial fingerprints; no order repair or financial action is claimed by this observation.

## Implementation boundary

The read-only frozen-attempt identity helper identifies a saved attempt even when Woo has replaced the native method; it grants no permission to pay or accept a notification. Existing paid-order checks, URL trust, native payment-method binding, per-order creation reservation and callback validation remain authoritative.

The native checkout route adapter separates a same-page method change before Woo mutates the old order. It preserves Woo authentication, nonce/cart-token processing, schemas and native order creation. Authenticated checkout GET/PATCH uses Woo's no-order flow. A changed-method POST, or same-method POST with changed address/checkout values, uses a separate native order. An unchanged same-method retry retains its payment fence. A durable non-autoload handoff slot and original-order lease keep stale duplicate requests on the same new native order rather than clearing a draft on every POST. Paid, foreign, ambiguous or expired successors are not replaced. Nonempty saved books whose identity cannot be verified cannot fall through into native mutation of that order.

Classic gateway feedback includes a nonce-bound native new-checkout link. Native Woo's `NoticeHandler` strips HTML when turning this notice into a Store API exception, so a link in that notice alone does not work in Checkout Blocks. The local Blocks presentation DTO now contains the separate checkout URL, without an order identity, provider URL or credentials. Its method component subscribes to Woo's documented `onCheckoutFail`, returns `true` to preserve the native failure, and renders the link itself. It accepts only an HTTP(S) URL on the current origin with the expected nonce/intent shape. Clicking navigates to checkout; neither the component nor the link submits a new payment. Plugin version 0.4.4 invalidates the prior checkout asset version.

The adapter matches only the exact native Checkout handler for `/wc/store/checkout` and `/wc/store/v1/checkout`. It does not take over other cart endpoints, third-party replacement checkout classes or order-pay. Existing guest order discovery still depends on the same Woo session; losing that session does not grant public order lookup.
