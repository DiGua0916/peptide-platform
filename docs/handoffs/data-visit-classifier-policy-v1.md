# Approved native visit classification — source checkpoint

072 adds Data-owned operational rules, not a fraud/human attestation or a reproduced Shopname algorithm. No schema, commerce, source-channel or storefront change is made. Runtime is unchanged until Root review/integration.

## Eligibility and rules

The native Tracker registers the classifier independently of the global tracking toggle so authorized operators can view settings while tracking is off. Automatic execution additionally requires tracking enabled, no decline/GPC/staff exclusion, installed storage, exact non-test visitor+visit ownership, an existing saved non-test client page_view, and a new persisted critical client event. Ingest calls the optional post-success hook only for genuinely inserted UIDs, grouped by original visit; duplicates and rejected batches do not call it. Optional read/write failures never alter the original client ACK, event, activity, PV or stage.

Approved default: enabled;60-second receipt window; more than120 distinct accepted rows means abnormal. Selected types: page_view, product_view, add_to_cart_attempt, checkout_submit_attempt, product_intent, product_favorite, product_share. The window is `(now-window,now]`. Heartbeat, visibility, video, server facts and classification events are ignored. Native unique visitor/event UID storage prevents retry fanout. Settings allow30–300seconds and20–500threshold.

Case-insensitive literal tokens: Googlebot,Bingbot,DuckDuckBot,Baiduspider,YandexBot,facebookexternalhit,Twitterbot. Matching is configurable by a separate switch and selected fixed tokens; no custom regex, generic bot/headless heuristic, IP or fingerprint inference. A matched selected token means abnormal/known_bot; otherwise excess count means abnormal/high_rate; other eligible visits mean normal/valid_visit. HeadlessChrome, unknown geography and missing observations do not imply abnormal. Raw UA/IP are never stored by this feature.

## Canonical evidence and immutable policy

Native option `peptide_core_visit_classifier_policy` stores version,enabled,window_s,threshold,bots_enabled,bots. An absent option uses approved defaults; malformed stored configuration disables automatic operation. Turning off preserves existing labels. First automatic verdict freezes canonical policy in that visit; later config changes affect newly classified visits only. Engine rule_version is `native-v1-` plus24 canonical SHA256 characters.

The old public four fields version/revision/status/rule_version keep their existing shape. Optional automatic extension is origin:automatic, reason:valid_visit|known_bot|high_rate, policy:{version,window_s,threshold,bots_enabled,bots}, evidence:{window_from_ms,window_to_ms,event_count,bot_token}. Bot token is null or an approved selected literal; no UA, IP, arbitrary rule text or extra fields survive. Optional manual extension is origin:manual,reason:manual_review. Canonical saved/replay/privacy export reuse the same parser.

Public REST remains native authenticated manage_woocommerce,64KB/batch20/rate600, unchanged ownership/test/UID/receipt-time protections. Public automatic-origin payloads are rejected; no anonymous classification route or admin impersonation exists. The server-internal automatic writer independently verifies privacy, owner/PV, frozen policy and actual persisted evidence. Old external clients retain responsibility for monotonic revisions.

Automatic normal uses revision1; abnormal uses revision2 and never automatically downgrades. Deterministic UID derives from owner+visit+rule_version+status. Repeated callbacks do not rewrite evidence or add another label. Any valid nonautomatic verdict stops future automatic updates. Manual correction chooses maximum revision+1 and requires the expected current maximum. All external, automatic and manual writes share one native MySQL named lock per original visit, namespaced by current database and tracking prefix/table; acquisition waits at most2seconds. Manual maximum/expected checks and insert run inside that guard, and automatic writes recheck manual/external priority and frozen policy inside the same guard. Thus a first automatic abnormal2 cannot slip between manual expected0 and manual1 insertion; the manual either becomes the current verdict or reports stale/unavailable. A previously computed automatic result cannot overwrite a later manual verdict. External API clients may still intentionally submit equal conflicting revisions; those remain visibly unclassified under the existing reducer. Existing highest-revision/received_ms exclusive cutoffs remain unchanged.

## Writer guard and reconnect behavior

The private persistence helper is unlocked only because every caller already owns the shared visit guard; no nested named locks or business transactions are introduced. Its actual INSERT uses `INSERT IGNORE ... SELECT ... WHERE IS_USED_LOCK(lockname)=CONNECTION_ID()`. This check is in the mutation SQL itself: a wpdb reconnect/retry that lost the original lock cannot insert. Zero inserted rows require an immutable existing winner for ACK; no winner is server_error/retry, not invented success. GET_LOCK timeout/SQL failure returns unavailable/retry; release is attempted in finally after successful acquisition. A release on a different connection cannot release another writer's lock. Public API permission, body/rate/batch limits and response shape remain unchanged. No old global UID lock or schema change is added; the guard serializes one original visit only.

## Operator and privacy

Data→访客判定 (`pc-data-visit-classifier`) requires native management permission. Native admin-post forms use action-specific nonce and PRG. Policy settings, disabled meaning,20-row visit pagination, current status/reason/rule/revision, frozen policy and bounded evidence are shown as readable window seconds, received count/threshold and matched token or none, only to authorized admins; no customer names/contact identities are listed. Manual normal/abnormal/unclassified explicitly records manual_review. Each row defaults to its current verdict; an unchanged abnormal/unclassified selection cannot silently become normal. The operator introduction explains the configured receipt-frequency and UA-token rules; a reported UA token is not authenticated identity. No DB IDs or nonces are sent to anonymous frontend.

Existing independent personal export includes canonical policy/evidence/manual reason in the customer's owner-bound event snapshot. Existing whole-event erasure/retention removes these records; no separate store/backfill or user identity retention is introduced. Conversion shared help integration is proposed separately under plans/072-shared-ui-integration.md to preserve071 ownership.
