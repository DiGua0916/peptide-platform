### 1.4 比对的局限

- 本机是 SQLite，不是 MySQL。两处 SQLite 和 MySQL 不一样的函数（`GREATEST`、`JSON_UNQUOTE`）和这次新发现的 `LPAD` 在本机用垫片补上，A、B 用的是同一套垫片。
- 数据是造的，量小。漏斗后四层“事件落到另一次访问里”这种边角在造的数据里没有出现，靠纯测试覆盖。
- 页面只比了服务端输出（页面外壳和交给脚本的配置），没有在浏览器里截图比；CSS 的变化是确定的，写在上表里。

### 5.2 打到 on 以后哪些数字会变（口径版本 2，11-13 晚重算）

三项口径所有者 11-13 定了，都和线上一致：订单按下单时间归属（改了代码）、弃单数包含召回成功的、排行支付成功率按下单时间。所以开到 on 以后，**“订单算在哪一天”不再变**。本机同一份数据上，同一版新代码 off 和 on 各读一遍，188 项里 55 项不同，原因只剩下面这几条：

| 变的原因 | 会变的数字 | 本机例子（今天） |
| --- | --- | --- |
| **已退款但付过款的订单算订单；销售额只减总后台标记的退款，不减 WooCommerce 里记的退款** | 订单数、销售额、客单价、商品件数和商品净销售额、排行的件数和金额、来源 / 落地页 / 分维度的订单和金额、实时卡片、趋势 | 一张在 WooCommerce 里全额退款 90 美元的单：订单 4 → 5，销售额 240 → 330，客单价 60 → 66 |
| 转化率 = 付了款的访客 ÷ 访客（原来是订单数 ÷ 访客）；一人多单只算一人，同一次访问里没有填地址记录的付款不算 | 概览页、运营数据、转化详情、来源、落地页、分维度、商品报表的转化率 | 19.05% → 23.81%（上面那张退款单的顾客算付款访客） |
| 漏斗后四层按每次访问结算 | 八层漏斗后四层 | 本机数据上没有变化（边角情况在纯测试里） |
| 概览页接口多一项 `metrics: { version: 2, mode: on }` | 不显示 | — |

**第一条要所有者先看**：线上如果在 WooCommerce 里做过退款（本机拷贝里就有），开到 on 以后这些单会重新算进销售额，数字比现在高。`docs/metrics.md` 第 6 节第 1 条一直是“待确认”：要么在总后台把这些退款补标，要么定成“WooCommerce 的退款也减”（改 `Metrics::order_fact()` 一处）。影子期对账里 `refund_basis`、`refunded_status` 两项就是这些单。

打到 on 本身是功能变化：要所有者看过影子期的差异后另外同意，逐店打开。
