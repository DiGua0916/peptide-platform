# Authenticated payment status returns — candidate, not deployed

Author: Codex. Task evidence: `D:/Codex/Tasks/2026-11-05/payment-return-repair`.

## Observed fault and verified limits

The owner saw the HQ-rendered “Check your payment status / We could not verify the return from the payment provider” page after a payment test. Read-only production inspection confirmed matching recent native paid attempts, applied reservations, and delivered HQ success events. The registered site identity and original encrypted return target validated. The browser failure therefore cannot be presented as a failed charge.

The existing HQ return handler conflates a rejected browser result with failure to read an already authenticated order's actual payment state. A rendered home link proves that its browser token and site checks passed, but not that the payment-provider result passed. Existing privacy logs omit query arguments and disable return-location logging. The actual missing or invalid `status`, `transaction_id`, or `sign` value was not retained; this task does not claim to have recovered it or changed the provider's signature contract.

## Candidate return contract

The original provider-signed `SUCCEEDED`/`FAILED` return path remains strict. When its result cannot be verified, an already authenticated HQ browser binding can instead receive a separate read-only status proof. The exact frozen native callback, site UUID/lifecycle, local reference and opaque native token remain mandatory. The check uses only `reference`, `token`, `check=1`, and `sign`; its signature binds `purpose=pc-panapay-return-check-v1`, `reference`, and `token` with the original frozen link key. It does not carry or synthesize a successful provider result. Provider notification parsing and financial authority are unchanged.

The store revalidates a fresh native order, the committed attempt book, native gateway, payment fingerprint, browser token, age and appropriate signature. A payment-confirmed view requires the exact returned attempt to be paid, its original provider transaction to match the persisted native transaction, and the corresponding transaction ledger entry to be applied. Unknown, failed and review states are derived from committed native state. No return handler invokes payment completion, CREATE, callback replay or an upstream retry.

## Result pages and cart boundary

Successful returns stay on the plugin's authenticated “Payment confirmed” view, with the order number and a safe shopping link. Unknown payments show “Confirming your payment” with a read-only recheck; confirmed failures retain a new-checkout path; inconsistent/cancelled/refunded results require review. Invalid browser bindings get the generic HTTP 400 view without private order data.

The handler deliberately avoids WooCommerce's `order-received` shortcode, whose unconditional cart emptying can discard a later cart. Cart cleanup requires the same verified paid attempt, the current browser's established Woo session and owner, nonconflicting order pointers, and a valid checkout-time cart snapshot. Relevant later cart mutations invalidate the snapshot permanently; matching contents alone cannot recreate it. Legacy sessions lacking that snapshot keep their cart. The scoped native clear filter also denies uncertain Panapay automatic cleanup, including on-hold payments; other payment methods retain native behavior.

The customer-visible pages are plugin PHP, not editable WordPress Pages. The generic HQ error HTML is `includes/class-payment-return-view.php::render()`, served by `rest_pre_serve_request`; authenticated merchant result HTML/text is `includes/class-callbacks.php::status_page()`. Copy, markup or styling changes require those source files or the plugin's translation catalog and normal code publication. No WordPress page-editor configuration is implied.
