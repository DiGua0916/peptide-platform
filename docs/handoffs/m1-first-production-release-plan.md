# 第一次上生产的方案（给平台所有者看，2026-11-13，F1）

**这份方案只写不做。** 每一步写了做什么、谁做、要你确认什么、大概多久、出问题怎么退。带 ★ 的是要你点头才会开始的步骤。

## 先说结论

- 新的发布方式在沙盒上已经跑通：一条命令 72 秒发完；故意放进去的两个错误都被自动拦住，6–7 秒退回旧版本。
- 第一次上生产分两次发，不要一次发完：
  - **第一次（打底）**：只发“现在的主线 + 发布工具自己”。顾客和投手看到的东西不变，目的是把 6 家店、开店模板、总后台都换到新的发布方式上，并把这几天按文件推漏的地方补齐。
  - **第二次起（逐个模块）**：一个模块合进主线、发一次。每个模块的新功能都带开关，发上去默认是关的，之后再按“关 → 影子 → 开”慢慢打开。
- 这样分的原因：第一次如果出问题，一定是发布方式的问题，不会和新功能的问题搅在一起。

发的内容：切换日当天的主线 + 发布工具（版本上报、发布记录、关键链路检查用到的两个小接口）。**没有任何模块的新功能。**

整个过程约 **30–40 分钟**，其中 15 分钟是试点店的观察时间。顾客在换代码的那一两秒里不会看到错误页（新旧目录是瞬间切换的）。

会留下的东西：试点店里一张待付款的测试单（不发邮件、不进弃单、不计入报表）；每台服务器上每份副本的一个回滚点（保留最近 3 个）；数据库快照文件。

**第一次有两处是没在生产上跑过的**，我会盯着：
- 测试单走到付款页那几步（沙盒只有货到付款，真实支付通道第一次跑，识别“刷卡框”的规则可能要调）。如果只是检查脚本认不出刷卡框而不是真的坏了，我会停下来告诉你，不会硬发。
- 多家店逐家发、开店模板、总后台这几段只做过离线测试。

## 第二次起：逐个模块

每个模块一次发布，流程和第一次一样（沙盒 → 试点店 → 其余店 → 主店 → 模板 → 总后台），每次都要你确认。发上去时开关都是关的，页面和现在一样（沙盒里已经逐字节比过）。

建议的顺序和理由：

| 顺序 | 模块 | 发上去以后 | 之后怎么开 |
| --- | --- | --- | --- |
| 1 | F4 指标口径（M6 / M7） | 开关关着，报表和现在一样 | 先在试点店开“影子”（两套口径同时算、页面仍显示旧数字），看几天差异都能解释，再开 |
| 2 | F2 价格引擎（M4） | 开关关着，价格和现在一样；顺带修好 5 家子店弹窗统计没记上的问题 | 试点店影子 24 小时 → 全部店影子 → 连续几天不一致为 0 再开 |
| 3 | F3 系列与订单（M3 / M10） | 所有店归入“系列 1”，不同步任何东西；订单开始汇总到总后台 | 订单回填（先试运行给你看数字）；系列同步要等你确认各店差异报告 |
| 4 | F5 投手后台、已购回访、商品地址（M9 / M11 / M14） | 三个开关都关着 | 投手版按账号逐个开（名单你定）；已购回访、商品地址按店开 |

F4 排第一是因为 F3 的报表和 F5 的投手首页都要用它的数字；F2 第二是因为它顺带修一个线上问题；F5 排最后是因为它改主题，影响面最大。如果你想让某个模块先上，可以调，只要 F4 在 F3、F5 之前。

每个模块发布前我会给你一页：这次发什么、沙盒结果、开关默认状态、回退办法。

## 回退办法汇总

| 情况 | 怎么退 | 多久 |
| --- | --- | --- |
| 发布过程中某家店检查不过 | 脚本自动把这家店换回旧目录，停下 | 沙盒实测 6–7 秒，生产估计 1 分钟内 |
| 发布完成后才发现问题 | 一条命令把这次发布换过的全部副本换回去（`release.py rollback`） | 几分钟 |
| 新功能开了以后有问题 | 把开关关掉，不用动代码 | 立刻（缓存页最多 5 分钟后跟着变） |
| 数据库 | 只加表加列，旧代码能在新结构上跑，所以回退代码不用动数据库 | — |
| 最坏情况：数据被改坏 | 用发布前的数据库快照恢复——会丢掉快照之后的订单，**恢复前一定先问你** | 视情况 |

## 发布窗口建议

按 6 家店近 7 天的访客数据（只读统计）：最安静的三个小时是 **北京时间 14:00–17:00**（美东凌晨 1–4 点），访客数不到最忙时段的一半。最忙是北京时间凌晨 3–5 点和上午 9–11 点（美东下午到晚上）。建议所有发布都放在北京时间下午 2 点到 5 点之间开始。
