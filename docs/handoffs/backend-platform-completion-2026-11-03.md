# Automatic two-host store provisioning — implementation in progress

2026-11-03 · Codex. User explicitly requested completing the remaining platform, including automatic store creation and account assignment. User has added wildcard DNS for the management and customer domains; both were independently observed returning the intended addresses through public DNS. Existing first-store business data is outside test scope.

The existing PHP Ops webserver driver requires deployment/database privileges in its runtime. This implementation instead adds an HQ admin-only form and a bounded private request queue. PHP never receives root SSH keys, global database permissions or arbitrary command execution. A separate root-owned worker allocates generated `sNNNN` identifiers and calls a source-address/key restricted, forced-command helper on the storefront server. Both workers consume strict schemas and root-only profiles, constrain paths/users/hostnames, preserve immutable ownership markers, and enforce a capacity limit. Each new store has independent users/salts/database credentials/media directories, dedicated FPM pools, exact HTTPS hosts, per-store SFTP exports and a host-only cookie boundary. Certificates use HTTP01 after wildcard resolution; no DNS API credential is needed for this topology.

The template importer reads only the platform master's four published design documents and referenced public raster images under its uploads root. It does not copy customer/order/product databases, private reports, connection identity or merchant settings. Image IDs are remapped in the new database. Native WordPress install, WooCommerce activation/pages, template publishing and HQ registration use existing APIs. Mail and async campaign execution start disabled; new shops receive no payment authorization.

Changed source: HQ `Admin/Provision_Page`, plugin boot hook; root deployment `tools/deployment/provisioning/worker.py`, template export/import helpers and boundary tests. Linux pure checks and PHP lint are the initial gate; real two-store creation, HTTP credential/nonce/cookie isolation, original-store preservation, browser editor save/publish and failure/retry checks remain pending at this checkpoint. SMTP/provider account inputs and real mail/payment acceptance remain external prerequisites; no real customer mail or charge is authorized by this checkpoint.

Root profiles/keys, queue password payloads, temporary native auth, SQL and generated credentials stay in private directories outside Git. Results never contain passwords. Successful jobs redact their account password. Do not describe this checkpoint as finished production provisioning.
