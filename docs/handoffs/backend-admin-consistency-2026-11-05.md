## Detail refresh optimization

Original customer detail only loaded once. Added tracking-refresh.js, enqueued after tracking-admin: single-flight snapshot+newest-event polling every5s while visible,12s abort timeout, pause/resume, online reconnect, pagehide stop/pageshow restart, visible last-updated clock explicitly labelled as browser local time. Store data clocks still show store timezone. Visitor rows/status update locally; live details-open state is restored rather than collapsed each poll. No long-lived PHP SSE request or Redis service is added. This is periodic detection, not zero-latency push; upstream event collection still affects freshness.

New events refresh a detail timeline quietly only when the reader is at its top with no open details/focus or older-page reading. Commit rechecks reading state after the request; if interaction began, queue a visible update notice. Explicit notice click uses force:true and intentionally returns to latest first page. Manual visit selection synchronously registers its target/loading; polling does not steal it. Quiet refresh does not invalidate an existing old-page request. Quiet request failure preserves current rows. User/cart/order data is never written by these tests.

Validation: refresh DOM12, detail race DOM11, existing live8/timeline24 and insights21 pass; source lint and deployment PHP lint pass. Actual production detail displayed automatic-update timestamp; pause was observed paused and explicitly resumed after a CUA timeout (not an app freeze diagnosis). No synthetic live client action was inserted, so do not claim click-to-server-to-admin latency benchmark or whole-backend performance certification. Actual browser tools remain slow at times.
