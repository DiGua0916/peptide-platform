## 2. 三项热修复在沙盒（MySQL）上实跑

做法：在沙盒里临时放一个假的 Facebook 像素（沙盒的对外请求是拦住的，不会真的发给 Meta），建 3 张带标记的订单和 1 个临时顾客账号；跑完全部删除、像素设置还原、页面缓存清掉。

### 员工不被追踪、不触发像素

| 检查 | 结果 |
| --- | --- |
| 判断函数：投手（角色 `pc_staff` + `pc_media_buyer`，前台没有 `manage_woocommerce`）算员工 | 通过 |
| 判断函数：管理员算员工；顾客、未登录不算 | 通过 |
| 像素开关：未登录访客、顾客 → 回传；投手、管理员 → 不回传 | 通过 |
| 真实请求，公开地址首页，未登录：发访客 cookie 1 次，页面带像素 | 通过 |
| 真实请求，公开地址首页，顾客登录：照常发访客 cookie、带像素 | 通过 |
| 真实请求，管理地址预览店铺，投手登录：页面 200，不发访客 cookie，页面不带像素 | 通过 |

**一个要让所有者和 F4 知道的事实**：带着员工登录状态去打开**公开地址**，店铺直接返回 403（“请用你的店铺管理地址”）。这是主线 11-03 就有的规则，不是这次改的，沙盒上实测如此。也就是说：

- 这个修复实际管用的场景，是员工**在管理地址里预览店铺**（实测通过）。
- 员工在自己电脑上直接打开公开店铺地址浏览时，登录状态只在管理地址有效，店铺认不出他是员工，**仍然会被算成普通访客、照常触发像素**。这一点这个热修复改不了，也不在它的范围里。如果要解决，需要另外的办法（比如按 IP 或按浏览器标记排除），属于新的决定。

### 测试单不发购买事件；补发不重复

购买事件一共四条路，逐条测了：

| 检查 | 结果 |
| --- | --- |
| 付款时服务端回传：普通单 → 打上“已回传”标记，后台待发队列 +1 | 通过（队列 0→1） |
| 付款时服务端回传：测试单（收件信息全填 1）→ 不标记，队列不变 | 通过（队列 1→1） |

| 补发任务：付款 20 分钟的测试单 → 仍然不发 | 通过 |

没测到的：

- 两条服务端回传同时发生的那个时间差（并发）没有实际制造出来，验证的是“10 分钟内不补”这条规则本身。
