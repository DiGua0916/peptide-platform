# Panapay 0.2：总后台统一支付部署与验收

按用户 2026-10-31 决定，支付方配置、创建支付、通知和分店账目由总后台统一处理。各独立站保留自己的 WooCommerce 客户、订单和库存。同一商户收款、各站分别记账，不执行支付方资金分账。

本文件替代 0.1 的各店商户配置指南。历史实现和检查点见 `docs/handoffs/backend-panapay-2026-10-31.md`。本机模拟验收不能替代目标服务器收款验收。

## 1. 两端安装

两端均安装 `peptide-panapay` 0.2，配套源码来自一致发布版本。

| 实例 | 必要组件与职责 |
| --- | --- |
| 总后台 | WordPress 6.7+、PHP 8.1+、AES-256-GCM OpenSSL、`peptide-hq`。保存商户配置、中央尝试、验签结果、持久回写事件及跨店账目；无需 WooCommerce。 |
| 店铺 | 配套 `peptide-core`、WooCommerce、付款连接器。保存原生订单/库存及支付尝试，核对所属付款结果；不保存新付款的支付方密钥。 |

当前核对 WooCommerce 11.2.1；隐藏原生电话时的条件字段回退要求 11.2+。保留原生 Checkout Blocks 及原确认项；原生电话隐藏时，只选该付款方式才补充必填电话。服务端拒绝缺少必要资料的请求。

原生 HPOS、CPT 均有处理路径，不为安装切换订单存储，不猜测第三方替代存储。

新的受控运维建店自动带入并启用付款连接器，沿用既有自动连接；运营人员不需要复制内部密钥。远程部署资料须含对应源码，旧准备任务的资料哈希与当前版本不一致时会拒绝，应重新准备，不覆盖哈希或强行续跑。

## 2. 总后台配置

唯一入口为 **总后台 → 支付中心**，`admin.php?page=pchq-payments`。仅 `manage_options` 管理员可查看跨店账目和提交设置，写操作要求 POST 和 nonce。

| 配置 | 规则 |
| --- | --- |
| 收款开关 | 默认关闭；关闭阻止新付款，在途通知、已保存事件继续处理。 |
| 允许收款店铺 | 明确授权注册店铺；新店默认关闭。 |
| 网关 | 支付方提供的公网 HTTPS 源地址，不含接口路径。 |
| 商户号、签名密钥 | 支付方提供；密钥加密且不回显，留空沿用。 |
| 测试模式 | 默认开启，生产禁止；不会自动切换支付方沙箱，须使用支付方确认的测试账户。 |
| 请求模式 | 文档中的 1=同步、2=异步，默认 2；均需有效通知确认付款。 |
| 可信收银台域名 | 网关域名自动纳入；额外域名先核实，再精确配置，无通配符或接口自动放行。 |
| 买家名称、说明 | 下发给被授权店铺，前端不下发商户或连接密钥。 |

店铺只显示统一管理提示，不再提供商户字段或本地配置写入口。HQ 连接失败时不静默回退本地商户。支付方仍须确认同一商户可用于相关店铺域名、业务和币种。

### 服务进程配置

总后台可用环境变量或同名 PHP 常量提供以下值；常量优先，服务配置优先于后台存储：

```text
PC_PANAPAY_GATEWAY=https://payments.example.com
PC_PANAPAY_MCHID=<支付方商户号>
PC_PANAPAY_SECRET=<支付方签名密钥>
```

示例不是有效凭据。不要向各店注入这些商户配置，不写进源码、仓库 `.env`、截图或日志；确认实际 PHP 网站进程可读取，交互式终端环境不代表 PHP-FPM 已读取。

各实例可设置 `PC_PANAPAY_ENCRYPTION_KEY`，值为恰好 32 字节独立密钥的标准 Base64。它用于本实例加密，和支付方签名密钥不同；HQ 与店铺可各自独立。未设置时由本实例 `wp_salt('auth')` 派生。迁移保留该实例原密钥或认证盐，当前无自动重加密工具。

## 3. 店铺身份与账号

每个中央尝试绑定 HQ 店铺编号、完整 UUID、原生订单号及站内支付引用，HQ 再生成全局引用给支付方。不能按单独数字订单号或可变域名匹配。

内部认证由系统管理：固定 HQ 地址，使用已接受的每店连接身份，签名绑定方法、路由、请求体摘要、时间及原子一次性 nonce；响应也签名并绑定请求 nonce。待确认的新密钥不能直接获得财务权限。删除、重新注册或身份变化不会把历史付款改派给新店。

销售账号由总后台账号页管理；专属入口服务端绑定店铺及账号，仍需 WordPress 验证账号、密码和已有认证过滤器。链接不是免密令牌或支付密钥，普通管理员及客户登录保持原流程。

生产的总后台、店铺和内部服务器请求均用有效公网 HTTPS。仅 `WP_ENVIRONMENT_TYPE=local` 的既定 `.local` 或回环连接允许本机 HTTP，不能通过改环境标识绕过生产要求；当前不自动适配任意私网目标。

## 4. 网络入口、WAF 与缓存

实际 URL 随实例生成，不套用本机端口或另一店地址。

| 实例与入口 | 方法 | 行为 |
| --- | --- | --- |
| HQ `/?rest_route=/pc-panapay/v1/hub/config` | POST JSON | 签名付款策略，不返回商户凭据。 |
| HQ `/?rest_route=/pc-panapay/v1/hub/session` | POST JSON | 签名创建申请，先保留占用再联系支付方。 |
| HQ `/?rest_route=/pc-panapay/v1/hub/session/status` | POST JSON | 只恢复已保存结果，不向支付方重建或查单。 |
| HQ `/?rest_route=/pc-panapay/v1/hub/notify` | POST 表单 | 支付方通知，验签并持久保存后精确返回纯文本 `ok`。 |
| HQ `/?rest_route=/pc-panapay/v1/hub/return` | GET | 验证尝试、令牌、返回签名，只读转回原店绑定页面。 |
| 店铺 `/?rest_route=/pc-panapay/v1/store/event` | POST JSON | 签名结果，只更新所属店铺的匹配尝试和订单。 |

WAF 对每个确切机器路由和 POST 方法允许服务器直接访问，无登录、验证码或浏览器 JavaScript 挑战；保留 TLS、WAF 和合适限流。不放开整个 `/wp-admin`、REST 或所有 API。按支付方 IP 限制前先取得正式地址范围，不自行猜测。

通知保持原 POST 表单和字段，不能被缓存、HTML 登录页、挑战或重定向替换；代理不得改写签名内部请求体。浏览器返回、原生 `order-pay`、结账及订单私有页绕过整页/CDN 缓存。反向代理使 WordPress 正确识别 HTTPS，避免生成 HTTP 地址或循环跳转。

收银台跨域需核实后加入精确信任列表。真实 iframe、三方验证和移动浏览器表现仍须现场验证。

访问日志、WAF、APM 及调试仅保留必要时间、路由、方法和状态摘要，不记完整 query、请求体、签名、密钥、回跳令牌、收银台 URL 或客户资料。默认完整请求行日志也需调整，不只关闭插件调试。

## 5. 创建保护及持久回写

HQ 结构版本 **2**：`pc_pay_hub_attempts` 保存中央尝试，`pc_pay_hub_events` 保存确认结果和回写事件，各实例使用自己的表前缀。店铺本地结构版本仍为 **3**。

- 店铺先持久保存订单及尝试；HQ 以店铺身份和引用建立唯一记录，并以 `active_order` 保留单订单创建占用。未知或中断不授权第二次远程创建。
- 创建成功只代表会话建立。同引用、同内容读取保存结果，内容冲突拒绝；超时不盲重发。
- 通知用尝试冻结的支付方凭据验签，先持久保存事件再返回 `ok`。成功交易及订单有唯一约束，重复通知不授予第二次完成机会。
- 店铺离线时事件保持待回写；重试使用稳定事件编号、新传输 nonce，目标仍需匹配原店编号和完整 UUID。
- 店铺继续用本地一次性完成保护与原生落库核对更新订单。支付方已确认、结果已投递、店铺已应用分别记录；需核账不等于订单完成。

两端财务核对使用独立、自动提交主库连接，不提交全局连接外层事务，也不将 WooCommerce、任意外部业务及提前执行的第三方钩子变成可自动回滚的跨服务事务。

### 生产定时任务必须落地

插件注册每分钟回写任务。生产须配置系统调度，每分钟执行到期 WordPress 事件或对应支付回写任务，并使用该实例正常配置。不要只依赖网页访问触发 WP Cron；注册了任务不等于无人访问时一定运行。

本轮未完成生产系统调度配置。应验证无人浏览、店铺离线恢复及进程中断重启后，事件仍能处理；监控待回写数量、最旧等待时间和需核对记录。支付中心“重试待回写结果”只重投保存通知，不创建新支付或清除财务占用。

付款和创建占用没有自动强制重置入口。状态不明、订单变化、交易冲突或身份改变时保留人工核账，先按支付方流水和原生持久订单核对，不靠删锁、删事件、删账本或重装绕过保护。向支付方确认通知重试周期及失败响应处理。

本轮已实现 **HQ → 店铺支付结果回写 outbox**。未来会员积分和外部自动履约仍需各自持久事件及幂等消费者，不能由浏览器返回发积分，也不能宣称任意外部业务可靠投递已完成。

## 6. 数据库与迁移连续性

各实例连接自己的数据库。原生单库沿用本实例 `DB_NAME`、`DB_USER`、`DB_PASSWORD`、`DB_HOST`。定制路由通过 `PC_PANAPAY_DB_HOST` 指明本实例同一数据库、同一 schema 的真实 writer；不能指向副本、另一店或影子订单库。WooCommerce 订单/尝试/核对也须使用该主库，不自动支持 HyperDB 或任意读写分离。

备份实例数据库、账本/事件、订单元数据和加密依赖。原店迁移保留身份，复制新店须生成新 UUID 与连接身份，不克隆客户订单或重用原身份。

0.1 在途付款保留原店 `pc_panapay_notify` / `pc_panapay_return`、冻结凭据、可信收银台及本地 `pc_panapay_transactions`、`pc_panapay_creations`、订单尝试。新中央付款与旧付款明确分支，旧请求不会自动改成中央尝试；旧付款核清前不能删除必要资料或回调。

迁移 HQ 保留中央尝试、事件及 HQ 原加密依赖；迁移店铺保留它自己的依赖。不能只搬当前商户号或重新生成认证盐。域名变化仅影响新会话，支付方保存的旧回调不会自动更新；需要旧入口时让 POST 直接到同一权威实例，不靠改变方法的跳转，不允许两份可写数据库处理同批付款。测试付款迁生产后不能当正式应收继续完成。

## 7. 隐私与账目范围

HQ 在内存中接收并转交协议所需金额、币种、商品、账单/收货地址、邮箱、电话及 IP/浏览器资料；完整创建体不保存为中央账本。列表只显示必要交易摘要，敏感 URL、验签凭据及交易资料按用途加密。

详细客户资料仍由所属 WooCommerce 店铺管理，不代表所有客户表已加密。生产仍需访问控制、最小数据库权限、加密备份、恢复演练及日志隐私配置。

金额按创建时订单分币种汇总，不跨币种相加。通知没有金额/币种字段，无法独立证明实结金额，到账需核支付方账单。查单、退款及分账协议未提供，因此没有自动查单、自动退款或资金分账；WooCommerce 手工退款记录不表示支付方已退款。

- [ ] 正式网关、商户、允许店铺域名、币种及精确信任的收银台域名由支付方确认。
- [ ] HQ 字符串 `order_id` 可被接受且由通知 `order_number` 原样返回，不能只凭数字示例认定。

- [ ] 同订单号分店隔离；未授权店、错误签名、重放及跨店引用拒绝。
- [ ] 实际订单存储及 Blocks 结账、电话/原确认项、税费/折扣/运费符合订单。
- [ ] 真实 redirect、iframe、手机、支付方验证、返回、卡支付及结算可用。
