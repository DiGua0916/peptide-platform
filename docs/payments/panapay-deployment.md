# Panapay 部署与验收说明

这份说明适用于每个独立 WooCommerce 店铺。支付插件不依赖本机域名，不把所有店铺的客户或支付配置集中到一个共享订单库。已有店铺迁移应保留其身份和账本；新店则独立安装、独立配置，并向支付方确认商户号是否允许用于该店。

当前实现与用户提供的创建支付、返回和通知协议对接。正式网关地址、正式商户参数、查单和退款接口尚未提供。本文中的验收项目均需在目标环境实际确认，不因源码存在、声明兼容或隔离本地 QA 完成而自动视为通过。

## 1. 服务器配置

安装 `wp-content/plugins/peptide-panapay`，使用 WordPress 6.7+、PHP 8.1+ 与支持 AES-256-GCM 的 OpenSSL。当前接口核对版本为 WooCommerce 11.2.1；原生电话字段隐藏时的条件字段方案要求 WooCommerce 11.2+。升级其他版本前，先在副本复核原生结账、设置和回调。

WooCommerce 原生 HPOS 与 CPT 都有处理路径，插件会读取当前权威订单存储，拒绝猜测第三方订单数据库。不要为安装支付插件临时切换订单存储或重置订单数据；在店铺实际采用的模式验收即可。

测试环境明确设置 `WP_ENVIRONMENT_TYPE=local` 或 `staging`。生产环境保持 `production`，使用正式商户并关闭插件测试模式。测试开关没有向支付方发送“沙箱”参数；是否为测试账户由支付方的网关和商户凭据决定。正式模式要求本站 HTTPS，网关和收银台也须为可信的公网 HTTPS 地址。

生产服务器可由受控配置注入以下值，示例均为占位内容，不能直接当凭据使用：

```text
PC_PANAPAY_GATEWAY=https://payments.example.com
PC_PANAPAY_MCHID=<支付方为该店提供的商户号>
PC_PANAPAY_SECRET=<支付方签名密钥>
PC_PANAPAY_ENCRYPTION_KEY=<32字节独立加密密钥的标准Base64>
```

同名 PHP 常量优先于环境变量；这三项支付连接配置优先于后台的同名值。`tag`、协议 `mode`、测试模式、额外可信收银台域名仍在 WooCommerce 的 Panapay 设置中管理。`mode=1/2` 表示同步/异步请求模式，两者都不能凭浏览器返回直接确认已付款。

多个站点共用服务器时，要按站点配置环境变量或私有常量；不能把同一组全局环境变量无差别覆盖所有店铺的后台配置。这里的多店铺是各店独立配置，不代表已提供 WordPress 网络级批量开通或共享商户配置功能。

签名密钥与插件加密密钥用途不同。独立加密密钥须恰好解码成 32 字节，保存为无多余空白的标准 Base64。它必须能被 PHP 服务进程实际读取；只在某个交互式终端设置，不代表 PHP-FPM/网站进程能读取。

后台保存签名密钥时使用加密存储，输入框不回显旧密钥；留空保持旧值。服务器已配置 `PC_PANAPAY_SECRET` 时，后台修改数据库副本不会覆盖服务器的值。不要把真实配置写进插件源码、仓库中的 `.env`、部署说明或公开日志。

### 数据库主库要求

财务完成占用与落库核对使用独立、自动提交的原生 `wpdb` 连接；已经写入的财务占用不会因全局 WordPress 连接的外层事务回滚而消失。默认支持本站原生单库连接，沿用 `DB_NAME`、`DB_USER`、`DB_PASSWORD` 和 `DB_HOST`，不在另一个数据库建立影子订单。

使用定制 `wpdb` 路由时，部署人员必须通过环境变量或同名常量 `PC_PANAPAY_DB_HOST` 显式指定真实 writer 主库。该地址仍须提供同一 `DB_NAME`、同一套 schema/表，且当前数据库凭据能够访问；不能指向副本、另一店数据库或另一个支付专用库。WooCommerce 订单与支付尝试本身的读写也必须落在这个同一主库，不能让核对读取副本的延迟状态。

`PC_PANAPAY_DB_HOST` 只明确独立连接的目标，不会改写全局路由，也不等于自动支持 HyperDB 或其他定制读写分离。必须先证明订单、尝试、账本和持久核对使用同一权威写库；无法证明时不要启用收款。独立财务占用也不使 WooCommerce 与所有外部业务形成一个跨服务原子事务。

## 2. 回调与支付页

插件用 `WC()->api_request_url()` 生成两个入口，并随创建支付请求发给支付方：

| 用途 | 方法与行为 |
| --- | --- |
| `pc_panapay_notify` | 服务端 POST 表单通知；验证后才可能执行付款完成，成功接受返回纯文本 `ok`。 |
| `pc_panapay_return` | 买家 GET 返回；检查签名和独立令牌，只读取/展示本站已确认状态，不根据返回参数把订单改成已付款。 |

不同固定链接设置可能生成 `/wc-api/pc_panapay_notify/`，也可能生成 `?wc-api=pc_panapay_notify`。部署时使用目标店铺实际生成的完整 HTTPS 地址，不手工套用另一店或本机的 URL。反向代理需要让 WordPress 正确识别 HTTPS，避免生成 HTTP 回调或产生重定向循环。

WAF 对**当前店铺确切的通知路径，或确切的 `wc-api=pc_panapay_notify` 参数，加 POST 方法**设置机器通知规则：该请求不应要求登录、验证码或浏览器 JavaScript 挑战。保留 TLS、WAF 检查和适合通知体量的流量限制；不要为此关闭整个 WAF，也不要开放整个 `/wp-admin`、`/wp-json` 或所有 `wc-api` 请求。若要加支付方 IP 限制，先取得支付方正式 IP 范围，不能自行猜测。

通知按所给协议使用 POST 表单字段，不能由代理强制改成 JSON。通知入口应直接返回插件结果，不能被缓存页、登录页、HTML 挑战或跳转替换。浏览器返回、原生 `order-pay` 付款页和其他原生 WooCommerce 私有结账页面同样必须绕过整页缓存/CDN 缓存；插件会发送禁止缓存与不索引响应头，边缘缓存仍需相应规则。

支付入口日志只保留排障所需的路径、方法、状态和时间等摘要。访问日志、WAF/APM 与请求调试工具不得记录完整 query、POST body、回跳令牌、签名、完整收银台 URL 或账单/收货资料。默认包含完整请求行的日志格式也需要调整；仅关闭插件调试开关不能清除边缘日志里的参数。

支付方返回的收银台域名可能不同于网关域名。向支付方确认后，在后台逐个填写精确可信域名；不能从接口返回值自动放行陌生域名。`iframe` 类型会使用原生订单付款页内嵌收银台，`redirect` 类型走原生结账跳转；目标浏览器、三方验证和收银台自身是否允许嵌入仍需现场验证。

## 3. 迁移已有店铺

迁移前后保留同一份 WooCommerce 订单、插件支付尝试元数据、站点身份、`pc_panapay_transactions` 交易账本和 `pc_panapay_creations` 创建占用表。当前数据库结构版本为 3。交易及创建占用的唯一约束是重复处理保护的一部分，不能删表重装来“清理卡住的订单”。升级或恢复也应连同这些数据核对。

如果使用 `PC_PANAPAY_ENCRYPTION_KEY`，目标服务器必须取得相同密钥。如果没有配置该项，当前实现使用 `wp_salt('auth')` 派生加密密钥，迁移必须保留原 WordPress 认证盐及相关配置。只复制数据库、重新生成认证盐或换成新加密密钥，会导致旧签名凭据与支付 URL 无法解密。当前没有自动重加密迁移工具；应在首次正式使用前确定密钥方案。

签名密钥可以经服务器配置提供，但已创建支付尝试还保留加密后的验签凭据，以处理在途结果。不能只搬当前商户密钥而遗漏用于解密历史尝试的密钥。

更换站点域名后，新支付请求会使用新回调地址；支付方保存的旧会话不会自动更新。存在未结束的正式支付时，先和支付方确认切换安排。需要保留旧域名入口时，应让其 POST 直接到达同一权威处理站点，不能只依赖可能改变方法的跳转，也不能让两份可写数据库并行处理同一批订单。

仍要使用的旧收银台域名，也需保留经支付方确认的精确信任配置；不能为了让旧会话继续而放开任意域名。

测试尝试保留测试标记，迁到生产环境后不能继续完成它们；不能将本地测试订单当作正式应收款继续支付。

## 4. 订单和异常处理

所有金额来自当前 WooCommerce 订单最终总额，商品行来自真实订单行，插件不在浏览器重算价格或替换商品内容。支付方需要的邮箱、电话及地址由服务端校验。原生电话字段隐藏时，插件才增加仅选择 Panapay 时显示、必填的电话字段；不会自动改动全站结账设置。不支持条件字段时，后台会提示恢复原生电话字段或使用受支持版本，缺资料的支付保持拒绝。

| 观察到的状态 | 处理方式 |
| --- | --- |
| 创建接口明确失败 | 买家看到启动失败提示；核对资料后可按原生订单流程重试，仍需尊重插件的尝试限制。 |
| HTTP 超时、响应不完整或执行中断 | 结果未知，支付方可能已经创建会话。保留原尝试，不自动重复创建；先在支付方后台按商户支付引用查账。 |
| 创建成功，尚无有效通知 | 订单尚未确认付款。浏览器“检查支付状态”只重读本站状态，不会调用支付方查单接口。 |
| 有效失败通知 | 可将仍待付款的对应订单尝试标为失败；晚到失败不能把已付款、已退款或已取消订单回退。 |
| 有效成功通知，内容和状态吻合 | 先取得持久的一次性完成占用，再调用 WooCommerce 原生付款完成；重复通知不会再次取得调用机会。 |
| 完成调用是否落库不明确，或订单/交易不一致 | 保留占用/核账记录，停止自动重复完成。按支付方流水和原生订单持久状态人工核账，不能仅靠刷新或删锁重试。 |

普通并发请求使用临时租约；持久的一次性完成占用不会因租约到期、服务重启或再次通知而自动释放。它限制本站重复执行原生付款完成流程，不保证支付方绝不会多扣款。额外交易与状态不一致需要核账。

创建支付另有持久的单订单占用，不依赖临时租约。仍在创建、执行中断或结果未知时，后来的请求不能自动重新调用创建接口；创建尚未完成时收到的通知暂缓处理并返回可重试错误。只有原尝试明确失败才允许按流程建立新尝试。没有强制重置入口，应先向支付方核对实际结果，不能靠删锁、删创建占用或刷新来绕过保护。

在后台订单的 Panapay 区域核对商户支付引用、状态和可用的交易信息。供应商未提供查单或退款 API，插件也没有自动查账、自动退款或强制重置完成占用功能。真实查账/退款应由授权人员在支付方后台完成，再按真实结果处理 WooCommerce 订单；WooCommerce 手工退款记录本身不代表支付方已经退回款项。

### 未来会员积分与自动履约

买家返回页不是业务事件源；不能因页面显示成功、URL 带 `SUCCEEDED`，就发放积分或派发履约。未来消费者可以接原生 WooCommerce 支付事件/状态，但须先核对权威主库中已经持久化的已付款结果，并按订单及业务动作去重，不能仅凭事件参数或内存订单对象判断。

原生进程内事件本身不提供任意基础设施崩溃下的可靠交付。若要在付款已提交、进程中断或消费者重复执行后仍保证积分/履约不丢失且不重复，需要额外实现与持久支付状态一致的 outbox、投递流程和按订单幂等的消费者。本轮没有实现这些耐久事件能力，也没有实现自动查单或退款；持久的一次性付款完成占用不能代替它们。

## 5. 正式启用前的实际验收

### 2026-10-31 最新开发验收

- 隔离支付 QA 的 HPOS 与 CPT 分别通过原生合同 39、故障 24、创建占用 20 个断言。两个存储覆盖了相同业务场景；断言数量不代表独立功能数量，供应商会话响应为受控模拟。
- CPT 数据库结构版本 2→3 的实际升级保留已有记录，只新增创建占用表并更新版本标记。目标店铺迁移仍需按自身数据另行验收。
- 真实两个 PHP 进程的通知竞态与创建竞态检查通过：临时租约失效不授予第二次完成或远程创建机会；未知状态保留核账。
- 本地实际 HTTP 回调 11 个断言及失败通知空交易号边界 4 个断言通过，包含方法/签名拒绝、精确 `ok`、重复通知、返回页及订单访问检查。原生 Store API 的电话及原有确认字段检查 7 个断言通过，合成结账订单保持待付款。
- 隔离 QA 的实际浏览器区块结账显示 Panapay；仅选择它时显示所需电话字段，切换银行转账后隐藏，原有确认字段保留。收银台仅使用模拟 `example.com` 会话；未在浏览器点击下单、输入卡号或收费，不把这项显示检查当成真实收款验收。
- 仅进行一次合成订单的真实创建请求，使用的是隔离支付 QA 的合成订单 55；没有输入卡号、没有发起收费。结果为 `http_request_failed`，未取得成功支付会话证据，也不能据此确认对端是否创建了会话，应按未知结果处理。
- 网关根地址的 HEAD 请求得到 302。根地址重定向不能证明目标 POST 创建接口、商户凭据或字符串引用已经可用。
- 公网 IPN、字符串支付引用兼容、正式商户及生产收款尚未验收。没有实现查单、退款 API 或耐久 outbox；本地验收不能替代这些能力。

### 目标环境待验收

以下项目尚需在对应目标环境逐项取得证据。源码检查、签名算法对照、模拟通知或新的隔离本地 QA 均不能替代这些验收。

- [ ] 支付方确认正式网关、商户配置、允许的店铺域名、币种及可信收银台域名。
- [ ] 支付方接受插件生成的字符串 `order_id`，并在通知 `order_number` 中原样返回；当前不能仅凭示例里的数字订单号认定字符串引用已被支持。
- [ ] 公网 HTTPS 通知从支付方实际发出，使用真实签名，完整到达正确店铺并收到纯文本 `ok`；无登录、挑战、缓存或重定向干扰。
- [ ] 原生区块结账完整保留原有确认字段，电话显示/隐藏和其他支付方式之间切换正确，金额/折扣/税费/运费不被支付插件重算。
- [ ] 在本站实际采用的 HPOS 或 CPT 模式完成支付会话、通知、库存和原生订单状态验证；若两种模式都要交付，分别验证。
- [ ] 实际 `redirect` 与支付方支持的 `iframe` 流程、浏览器返回、移动端及支付方验证页面可用。
- [ ] 重复通知、并发通知、晚到失败、错误签名、串订单引用、改动后的订单，以及完成过程中断都符合停止/幂等/核账规则。
- [ ] 在副本完成迁移恢复，旧加密资料可读取、在途引用可匹配、只有一个权威订单处理站点；正式配置与测试配置分开。
- [ ] 原生单库或已明确配置的 writer 目标一致；订单、支付尝试和账本均使用同一权威主库，不能以设置了 `PC_PANAPAY_DB_HOST` 代替这项验证。
- [ ] 供应商明确通知中不含金额/币种的处理约定，以及人工核账流程。当前通知签名只覆盖 `order_number/status/transaction_id`，无法从通知独立证明实际结算金额或币种；浏览器返回签名更不绑定订单。

在查单、退款及更完整的金额/币种核验协议提供之前，不把这些能力写成自动功能，也不把测试商户、测试卡或本机回调结果列为生产收款通过。
