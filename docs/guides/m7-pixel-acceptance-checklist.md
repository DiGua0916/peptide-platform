# 像素与 CAPI：逐店配置和验收清单（FE-09）

给平台所有者。每家店做一遍，做完在最后的表里打勾、存好截图。2026-11-10，F4「数据」会话。

- 像素 ID 和访问口令（CAPI 令牌）由投手或你自己在店铺后台填，开发不经手、不保存。
- 怎么在 Meta 那边拿到像素 ID、访问口令、测试事件代码，见 [投手教程](facebook-pixel-capi-投手教程.md) 第一节，这里不重复。
- 本清单里的“验收脚本”“发送测试事件”按钮、服务端 AddPaymentInfo 是新代码（分支 `claude/m6-metrics-db7036`），**发布到这家店之后才能用**；发布前只能做第 1、2 步。

验收标准（PRD FE-09）：在事件管理工具里，六种事件——PageView、ViewContent、AddToCart、InitiateCheckout、AddPaymentInfo、Purchase——每一种都是“浏览器 + 服务器”两路，并且去重正常。

## 1. 准备（Meta 这边）

- [ ] 这家店用哪个像素（数据集）已经定了，像素只给这一家店的域名用。
- [ ] 拿到三样东西：像素 ID、访问口令（`EAA` 开头）、测试事件代码（`TEST` 开头）。
- [ ] 店铺域名已经在商务管理平台做过域名验证（没做的话广告能投，但事件优先级配不了）。

## 2. 填进店铺后台

店铺后台 → 店铺设置 → 系统设置 → 广告像素。

- [ ] Facebook 卡片 →「新建像素」：填像素 ID 和访问口令。**关联域名留空**（留空就是本店域名；填成别的域名，服务器不会给这个像素回传）。
- [ ] 右上角「统计设置」：
  - [ ] 勾上「服务端也回传 PageView」（不勾的话 PageView 只有浏览器一路，验收过不了）。
  - [ ] 「高级匹配」保持勾选。
  - [ ] 「遵守 GPC」保持勾选；「员工访问也回传」保持不勾。
  - [ ] 「Facebook 测试事件代码」填上刚才那串 `TEST…`（验收完要清空，见第 6 步）。
- [ ] 点「保存」。保存后令牌只显示前 6 位，这是正常的。

## 3. 先看通不通（一分钟）

- [ ] 广告像素页面上点「发送测试事件」。页面顶部显示：
  - **已通**：往下做。
  - **未通**：按提示改。最常见的是访问口令复制不全、口令不是这个像素生成的、像素 ID 多了空格。改完先保存再测。
- [ ] 事件管理工具 → 这个像素 →「测试事件」里能看到一条来自服务器的 PageView。

## 4. 走一遍完整下单

需要有人能在服务器上跑命令（F1 发布会话或开发）。在这家店的目录里：

```bash
wp eval-file wp-content/plugins/peptide-core/tests/m7-pixel-acceptance-smoke.php start
```

命令会给出一个带验收码的店铺链接，30 分钟内有效。

- [ ] 用**手机**打开这个链接（最好把链接发到 Facebook / Messenger 里再点开，这样是在 FB 内置浏览器里，和真实顾客一样）。不要用登录了后台的浏览器，员工访问不回传。
- [ ] 依次做：打开首页 → 点开一个商品 → 加入购物车 → 进入结账 → 填真实格式的地址（**不要全填 1**，全填 1 是测试单，不算数） → 选支付方式 → 下单并付款（用真卡小额，或沙盒的测试支付） → **付款后回到店铺的“下单成功”页**再关。
- [ ] 回到服务器核对：

```bash
wp eval-file wp-content/plugins/peptide-core/tests/m7-pixel-acceptance-smoke.php check
```

每种事件一行，写着“通过”或者哪里没通、该查什么。六行都是“通过”、最后一行是“结果：通过”才算过。
没有通过时按提示处理，然后从 `start` 重新来一遍（验收码每次都是新的）。

也可以不看命令行：广告像素页面最下面的「服务端回传记录」里，验收期间会同时列出平台是 Facebook（服务器发的）和 browser（验收浏览器发的）的记录，同一种事件两边的记录应该成对出现。

## 5. 在事件管理工具里核对

事件管理工具 → 这个像素 →「测试事件」（因为填了测试事件代码，服务器事件会出现在这里；浏览器事件需要在这个页面里输入店铺网址点「打开网站」再走一遍，才会显示在同一个列表里）。

- [ ] 六种事件都出现了。
- [ ] 每种事件的“接收来源”有 **浏览器** 和 **服务器** 两路，其中一条标着**已去重**（Deduplicated）。
- [ ] Purchase 的金额、币种（USD）对，订单号对。
- [ ] 截图存档：测试事件列表一张（六种事件都在）、Purchase 展开详情一张。文件名带店铺编号和日期，例如 `s0006-fb-events-2026-11-12.png`。

过一天再看「概览」：

- [ ] 六种事件的“事件匹配质量”有分数；Purchase 的分数明显低（比如 5 分以下）时告诉开发，多半是邮箱、电话或 fbp / fbc 没传到。
- [ ] 「诊断」里没有“服务器和浏览器事件没有去重”之类的警告。

Meta 的界面文字会变，上面几处名称对不上时以“每种事件有浏览器和服务器两路、并且去重”为准。

## 6. 收尾

- [ ] 清空「Facebook 测试事件代码」并保存。**不清的话正式事件会一直进“测试事件”，广告学不到转化。**
- [ ] 结束验收：

```bash
wp eval-file wp-content/plugins/peptide-core/tests/m7-pixel-acceptance-smoke.php stop
```

- [ ] 在事件管理工具的“汇总事件衡量”里把 Purchase 排在第一位（投手教程第五节）。
- [ ] 验收用的那张订单：真卡付的就按正常订单处理或在总后台标记退款；不要删订单。

## 8. 常见情况

| 现象 | 原因和处理 |
| --- | --- |
| 六种事件都“服务端没发” | 没填访问口令；或关联域名不是本店域名；或后台任务没在跑（让开发看 Action Scheduler）。 |
| 只有 PageView“服务端没发” | 「服务端也回传 PageView」没勾。 |
| AddPaymentInfo“event_id 不一致” | 浏览器没拿到服务器生成的事件，自己补发了一条。偶尔一次是网络问题，重做一遍；每次都这样告诉开发。 |
| Purchase“浏览器没发” | 付款后没有回到店铺的下单成功页。跳转收银台的支付方式要等它跳回来。 |
| Purchase“服务端没发” | 订单没有真的变成已付款；或者下单时这个浏览器发了 GPC / 退出信号；或者用的是员工账号。 |
| 发送测试事件“未通（HTTP 400）” | 访问口令或像素 ID 不对，提示里有 Facebook 返回的原因。 |
| 事件管理工具里服务器事件有、浏览器事件没有 | 浏览器装了广告拦截，或者是在登录了后台的浏览器里测的。换手机测。 |
