# 指标口径（M6，NF-02）

口径版本 1 · 2026-11-10 · F4「数据」会话。和开发文档 v1.1 第 6 节、PRD v1.1 第 7 节一致；口径要改，先改 PRD 和开发文档，再改本文件和 `Data\Metrics::VERSION`。

每个指标只在一个地方算：`PeptideCore\Data\Metrics`（`wp-content/plugins/peptide-core/includes/data/class-metrics.php`）。
店铺后台的概览页和数据页、投手首页（F5）、订单上报和总后台报表（F3）都调用它，函数签名见 `docs/CONTRACT.md` 的「M6 / M7」一节。

## 1. 通用约定

| 项 | 约定 |
| --- | --- |
| 时间段 | `[from, to)`，Unix 秒。“今天 / 昨天 / 近 7 天 / 近 30 天”按店铺时区（`Metrics::window()`，和概览页同一个算法） |
| 金额 | 美分整数（`*_cents`），订单币种 |
| 比率 | 百分数，保留 2 位；分母是 0 时为 `null`（页面显示“-”），不显示成 0% |
| 访问归属 | 访问按开始时间（`start_ms`）落在时间段内算；这次访问后来走到哪一步，都记在这一批里 |
| 订单归属 | 按付款时间（`date_paid`）落在时间段内算。已付款状态但没有付款时间的订单（导入、手工改状态）按创建时间 |
| 测试单 | 以下任一种都不计入订单、销售额、客单价、转化率，漏斗只计到“发起结账”：订单标记 `_pc_test_order = 1` 或收件信息（姓、名、地址、城市）全填“1”；付款方式名称以 “Test payment” 开头；包含演示商品 |
| 爬虫 | 在写入时排除：`Tracker::is_automated()` 认出的爬虫、扫描器、无头浏览器不会产生访客行，所以读数时不用再筛 |

## 2. 七个指标

| 指标 | 计算 | 数据源 | 入口 |
| --- | --- | --- | --- |
| 访客 | 时间段内有访问的不同访客（`pc_track_visitors`），只算 `is_test = 0` 且访客行还在的 | `pc_track_visits`、`pc_track_visitors` | `Metrics::visitors()` |
| 转化率 | 支付成功访客 ÷ 访客 | 同上 + 订单 | `Metrics::conversion_rate()` |
| 订单 | 收到过支付成功通知的订单：状态是已付款（处理中 / 已完成等 `wc_get_is_paid_statuses()`），或状态是已退款但有付款时间；去掉测试单。待付款、失败、取消、保留都不算 | WooCommerce 订单 | `Metrics::orders()` |
| 销售额 | Σ 订单金额 − Σ 已标记退款（订单元 `_pc_refund_cents`，由总后台回写，不超过订单金额） | WooCommerce 订单 | `Metrics::orders()['sales_cents']` |
| 客单价 | 销售额 ÷ 订单数（四舍五入到分）；没有订单时是 0 | — | `Metrics::orders()['aov_cents']` |
| 弃单数 | 弃单列表去重后的条数：一位顾客一条，不含已作废和测试单 = 待召回 + 召回中 + 召回失败 + 召回成功 | `Recovery_Items::list()` | `Metrics::abandoned()['count']` |
| 召回激活率 | 召回成功 ÷ 发过召回邮件的弃单（召回中 + 召回失败 + 召回成功） | 同上 | `Metrics::abandoned()['rate']` |

**支付成功访客**（转化率的分子，也是漏斗最后一层）：这位访客在时间段内有一次访问同时满足——访问走到已付款（`stage ≥ 5`）；
同一次访问里有填地址的记录（`checkout_address_completed`）；关联的订单里有一张是已付款的非测试单；这张订单上记的访客和访问就是这一次。
“关联的订单”= 这次访问的付款事件里出现过的订单，加上访问上最后挂的那张（同一次访问里先付了一单、又下了一张没付的，访问上只留后一张）。
一人付了几单只算一人。

**ROAS**（销售额 ÷ 广告花费）在总后台算（`pchq_ad_spend`），店铺端只提供销售额。

## 3. 八层漏斗（FE-05）

`Metrics::funnel()`。按不同访客计，每一层都是上一层的子集，所以**每一步不会大于上一步**。

| 层 | 条件 | 事件 | 回传 FB |
| --- | --- | --- | --- |
| 1 访问 | 有访问 | `page_view` | PageView |
| 2 看商品 | `stage ≥ 1` | `product_view` | ViewContent |
| 3 加购 | `stage ≥ 2` | `add_to_cart`（服务端） | AddToCart |
| 4 发起结账 | `stage ≥ 3` | `checkout_view` | InitiateCheckout |
| 5 填地址 | 第 4 层，且同一次访问里有 `checkout_address_completed` | 只记内部 | — |
| 6 选物流 | 第 5 层，且同一次访问里有 `checkout_shipping_selected`；或这次访问支付成功 | 只记内部 | — |
| 7 选支付 | 第 6 层，且同一次访问里有 `checkout_payment_selected`；或这次访问支付成功 | `checkout_payment_selected` | AddPaymentInfo |
| 8 支付成功 | 见上面“支付成功访客” | `payment_success`（服务端） | Purchase |

- 结账页一打开就带默认的物流和支付方式，那不是顾客的动作：没有填地址的记录时，第 5–8 层都不算。
- 付了款的访问一定选过物流和支付方式，所以第 6、7 层对已付款的访问不要求浏览器事件（浏览器事件可能丢）；但**填地址的记录不能少**。
- 访问关联的订单全是测试单，或者都已经被删掉：这次访问只算到“发起结账”。

### 推进规则（写入侧）

访问的 `stage` 只升不降：1 看过商品、2 加购成功、3 进入结账、4 下单（选定支付并提交）、5 支付成功。
要升到 4 或 5，这次访问里必须已经有 `checkout_address_completed`，否则**只记事件、不推进到 4、5**，并记一次异常（`Tracking\Funnel_Guard`）：

- 这时最多记到 3：下了单本身说明这位访客到过结账页，所以浏览器的结账事件一条都没到的订单（以及测试单）仍然留在“发起结账”里。
- 订单号仍然会挂到这次访问上（弃单和漏斗明细靠它找订单）。
- 填地址的事件晚到（浏览器攒批上报，下单比上报还快）时，事件一到就补推进，并把这次异常记为“已补上”（一批里有几条填地址事件也只记一次）。
- 测试单不推进到 4、5，也不算异常。
- 异常计数：`Funnel_Guard::counters()`（按天，写入时累计）和 `Funnel_Guard::anomalies( $from, $to )`（按事件表现算的准确数）。
  异常多说明“填地址”事件没有稳定上报，需要查前端埋点，而不是放宽规则。

这条规则受 M6 开关控制（见第 5 节）：关着时和现在完全一样（`GREATEST` 推进）；影子模式照旧推进，只记“如果拦会拦掉多少”；开了才真的拦。

## 4. 和旧口径不一样的地方

旧口径指概览页（`Overview::range_data()`）和运营数据（`Data\Operations::period()`）现在的算法。

| 指标 | 旧 | 新 | 影响 |
| --- | --- | --- | --- |
| 订单归属时间 | 创建时间 | 付款时间 | 晚付款的订单（召回、付款帮助信之后付的）从创建那天挪到付款那天；过去某天的数字不会再被以后的付款改动 |
| 测试单 | 只认测试付款方式和演示商品 | 多认收件信息全 1 的测试单 | 店主自己测支付的单不再算进销售额和订单数 |
| 已退款订单 | 状态变成已退款后不再算订单 | 付过款就算订单，销售额减已标记退款 | 全额退款的单：订单数 +1，销售额 +0 |
| 退款金额 | WooCommerce 里记的退款 | 总后台标记的退款 `_pc_refund_cents` | 系统内不做退款（PRD Q16），正常两边都是 0；WooCommerce 里若有历史退款，新口径不减 |
| 访客 | 不看 `is_test`，访客行被清掉的访问也算 | 只算 `is_test = 0` 且访客行还在的 | 生产店都是 `is_test = 0`，通常没有差别 |
| 转化率 | 订单数 ÷ 访客 | 支付成功访客 ÷ 访客 | 一人多单只算一人；访问里没有填地址记录的付款不算 |
| 漏斗“支付成功” | 有付款事件就算，可能比“选支付”多 | 必须先有填地址的记录，且不会超过上一层 | 见第 3 节 |
| 弃单激活 | 弃单邮件序列表 `pc_recovery`（一次结账一条） | 弃单列表 `Recovery_Items`（一位顾客一条；付款帮助信、手写信也算召回） | 两个数据源，数字会不同，以弃单列表为准 |

逐张订单把差异归到上面的原因：`Data\Metrics_Reconcile::report( '30d' )`。归不进任何原因的订单会列在 `unexplained` 里——这个列表必须是空的才能往下走。

## 5. 开关：关 → 影子 → 开

每家店一个选项 `peptide_core_m6_mode`（`off` 默认 / `shadow` / `on`），由 `Data\Metrics_Switch` 读取：

| 档 | 页面显示 | 漏斗推进 | 记录 |
| --- | --- | --- | --- |
| `off` | 旧值；新算法一次都不调用 | 和现在一样 | 无 |
| `shadow` | 旧值 | 和现在一样 | 新旧不一致写进对账日志；漏斗记“如果拦会拦掉多少” |
| `on` | 新值（新算法出错时退回旧值） | 没有填地址记录就不推进到 4、5 | 继续对账 |

```bash
wp option update peptide_core_m6_mode shadow
```

```bash
wp eval 'print_r( PeptideCore\Data\Metrics_Switch::log() );'
```

出问题时把选项改回 `off` 即可，不用回滚代码。历史事件不动；新口径从打开那天起生效，历史报表可以用 `Metrics_Reconcile` 按新口径重算作对照。

已经接入开关的页面和还没接入的报表清单见 `docs/handoffs/m6-metrics.md`。

## 6. 待确认

1. **WooCommerce 里的历史退款**：新口径只减总后台标记的退款。如果生产库里有 WooCommerce 退款记录，要么在总后台补标，要么决定把它们也减掉（改 `Metrics::order_fact()` 一处）。脱敏快照到了之后用 `Metrics_Reconcile` 的 `refund_basis` 一栏看有没有。
2. **填地址事件丢失时的付款**：按开发文档，访问里没有填地址记录的付款不算进漏斗“支付成功”和转化率（订单数和销售额不受影响）。影子模式会给出这类付款的数量；如果比例高，先修前端上报，或者改成“订单上有完整收货地址也算填过地址”（服务端补记），需要平台所有者定。
3. **保留（on-hold）订单**：现在不算已付款。如果以后有先发货后确认收款的支付方式，需要重新定。
