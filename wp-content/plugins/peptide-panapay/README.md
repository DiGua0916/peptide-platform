# VialCove Panapay 支付 0.4

支付由总后台统一管理，各独立站保留自己的 WooCommerce 订单、库存和客户资料。同一插件在总后台运行支付中心，在店铺运行付款连接器；总后台无需 WooCommerce。

总后台保存商户配置、创建支付会话、接收支付方通知，并持久保存等待回写店铺的结果。可添加多个独立配置的付款账号；交易绑定账号、原生付款方式、店铺编号、完整 UUID 和站内支付引用。A、B 两站即使订单号相同也分别记账。这里的分店统计不执行资金分账。

卡号和安全码在支付方收银台输入，本站不提供收卡表单。当前协议只有创建支付、浏览器返回和结果通知，没有自动查单、自动退款或支付方分账接口。

## 安装与配置

两端均安装并启用 `wp-content/plugins/peptide-panapay`，使用 WordPress 6.7+、PHP 8.1+ 和支持 AES-256-GCM 的 OpenSSL。

| 位置 | 依赖与职责 |
| --- | --- |
| 总后台 | 已启用 `peptide-hq`；管理商户配置、允许收款的店铺、通知、分店交易及回写。无需 WooCommerce。 |
| 独立站 | 配套 `peptide-core` 与 WooCommerce；保留原生 Checkout Blocks、订单和库存，联系固定总后台付款。 |

当前 WooCommerce 接口核对版本为 11.2.1；原生电话隐藏时的条件字段回退要求 WooCommerce 11.2+。支持原生 HPOS/CPT，不猜测第三方替代订单存储。

从 **0.3 升级到 0.4，先升级总后台，再升级店铺连接器**。总后台保留旧 `/hub/config` 的默认账号七字段策略；新店铺改用 `/hub/methods` 多付款方式策略。新连接器遇到新接口不存在、网络或认证失败时不会回退旧接口或另一商户。若仍在 0.2，先按旧版顺序把店铺、HQ 升至 0.3，再执行本次 HQ 优先升级。

唯一商户配置入口为 **总后台 → 支付中心**，页面标识 `pchq-payments`。点“添加付款方式”，填写支付方参数和买家付款名称，再保存；可继续添加，每项独立编辑、开启、关闭或归档。新添加的方式默认关闭收款、默认同步全部已接受的店铺（含以后接入的店铺）；也可取消“全部”，指定店铺。旧单账号导入为 `default`，保留原收款开关、测试模式和指定店铺，不自动扩大授权。

店铺沿用已有自动接入总后台的连接，不需要运营人员复制内部密钥。店铺付款设置仅显示统一管理提示，不提供商户号和密钥输入；总部不可用时不会静默退回本地商户。新运维建店自动包含并启用连接器；远程部署资料仍须含对应源码，旧准备任务与当前资料哈希不一致时安全拒绝，不能强行续跑。

测试模式默认开启，用于标识并限制测试商户，不会自动切换支付方沙箱。生产禁止测试模式，正式收款要求总后台和店铺使用 HTTPS。网关、收银台始终为公网 HTTPS；只有 `local` 环境的既定 `.local` 或回环内部连接允许本机 HTTP。

## 多付款方式与结账展示

当前接入协议固定为 **网关协议（当前文档）**。每项可填写自己的网关、商户号、签名密钥、tag 和请求模式。账号名称只作总后台内部备注，不替代商户号，也不发送为支付方请求字段。密钥不回显，留空保留原值。

新方式只有显式勾选“开启此付款方式”才启用；列表也可单独切换。关闭或归档只阻止新支付，保留历史及在途处理。最多保留 20 个身份（包括归档）；不硬删除、不复用 ID。导入账号 ID 为 `default`，其余为随机 32 位小写十六进制；对应原生网关为 `pc_panapay` / `pc_panapay_<id>`。

保存后授权店铺自动读取签名展示策略（短期缓存上限 60 秒），不接收商户密钥。不同付款方式在原生结账中分别选择，订单冻结所选账号和原生网关，不能把同一待处理尝试切换到另一个渠道继续付款。设置使用版本与 CAS 防止不同窗口覆盖；表单支持焦点、Escape/取消恢复草稿及无 JavaScript 内联提交，写入要求管理员权限和 nonce。

可选的展示图标精确为 **American Express、Mastercard、Visa、Discover、Apple Pay、PayPal** 六种。这些本地图标只控制结账展示，不表示已独立接入 Apple Pay 或 PayPal，也不会替支付方开通渠道；实际可用付款方式由支付方账户与收银台决定。

支付窗口高度默认 **530px**，只接受 **320–1600** 的整数，并在创建尝试时冻结。它只影响支付方实际返回 `iframe` 类型的窗口；修改配置不会改变已创建尝试的高度，也不会把 `redirect` 强行改成嵌入。同步/异步仍是文档的请求模式，不是付款成功依据；本插件没有额外“快捷支付”实现。

已归档条目右侧可点“恢复”。恢复沿用原账号 ID、商户参数和历史记录，并保持关闭；核对后再单独开启。

## 凭据、数据库和迁移

支付方密钥只在总后台保存，采用加密存储、不回显，设置框留空沿用。总后台服务进程可用环境变量或同名 PHP 常量提供 `PC_PANAPAY_GATEWAY`、`PC_PANAPAY_MCHID`、`PC_PANAPAY_SECRET`；常量优先。这些覆盖仅作用于导入的 `default` 账号，不覆盖新添加账号；不应注入各店。

`PC_PANAPAY_ENCRYPTION_KEY` 是各实例本地加密用的独立 32 字节密钥，采用标准 Base64，和支付方密钥不同。各实例可以各自独立；迁移某实例必须保留它原有的加密依赖。未显式配置时使用该实例的 `wp_salt('auth')` 派生，需保留原 WordPress 认证盐。当前无自动重加密工具。

两端财务写入和核对使用本实例权威主库的独立、自动提交 `wpdb` 连接。定制路由须用 `PC_PANAPAY_DB_HOST` 指明该实例同一数据库、同一 schema 的真实 writer，并保证原生订单读写也到该主库；此项不自动支持任意读写分离。

多账号配置由 `Hub_Accounts` 的版本化选项 `pc_panapay_hub_accounts` 管理；旧 `Hub_Settings` 仅用于历史导入和默认账号服务配置覆盖。首次迁移保留旧参数，不删除旧选项。

总部结构版本为 3，包含 `pc_pay_hub_attempts`、`pc_pay_hub_events`：持久单订单创建占用、跨账号的成功交易/订单唯一约束及结果回写 outbox。0.4 新增账号归属与加密冻结的可信主机；编辑或归档账号不会改变在途付款的密钥、域名和窗口高度。店铺本地结构版本仍为 3。0.1 在途付款继续使用原店回调及冻结凭据，不能删旧 `pc_panapay_transactions`、`pc_panapay_creations`、订单尝试或加密资料，也不自动把旧付款改派成中央付款。

旧店迁服务器保留身份，新店克隆生成新 UUID 和连接身份。域名变化只影响新生成的回调；支付方已经保存的旧地址不会自动改变，必须保持在途入口连续，且同一批订单只能有一个权威处理实例。

## 付款与回写

店铺先保存订单及支付尝试，再向固定总后台发起签名请求。总后台核对已接受身份与收款授权，先保留创建占用，再联系支付方。创建接口 `SUCCEEDED` 只代表会话建立。买家进入支付方 `redirect` 或受原生订单访问检查保护的 `iframe` 页面。

支付方 POST 表单通知到总后台 `/?rest_route=/pc-panapay/v1/hub/notify`。总后台用该尝试冻结的支付方凭据验签，先持久保存结果事件，再返回纯文本 `ok`；之后向所属店铺发送签名结果，由店铺一次性完成保护及原生落库核对控制订单、库存更新。

店铺离线时结果留在总后台等待回写。支付中心分别显示“支付方确认”和“店铺回写”；重试只投递已保存结果，不重新创建支付。生产必须配置系统每分钟执行到期 WordPress 任务，不能依赖有人浏览页面触发 WP Cron，并应监控待回写和需核对记录。

浏览器返回经总后台验证后回到原店绑定返回页，只读展示，不授权付款。未知会话恢复只读取总部已保存结果，不是支付方查单。超时、中断、交易冲突或完成状态不明确时保留占用和核账证据，没有强制重置入口，不通过删锁、删账本或重装来重试。

## 权限和隐私

总后台商户设置及跨店账目仅供管理员。销售账号在总后台管理，专属登录入口由服务器绑定具体店铺和账号，仍须验证账号密码；链接不是免密令牌，普通管理员和客户登录保持原流程。

总后台在内存中接收并转交支付方协议所需订单、账单/收货地址、邮箱、电话及 IP/浏览器资料，不把完整创建请求体保存为中央账本。列表仅显示必要交易摘要；签名凭据、会话/返回 URL 和必要交易资料按用途加密。前端付款配置不含商户或连接密钥。这不等于 WooCommerce 所有客户表已加密。

日志不得记录完整支付请求体、签名、密钥、回跳令牌或完整收银台 URL。未来积分和外部履约仍需自己的持久事件及幂等消费者；本轮已实现的是支付结果回写 outbox，不代表积分或任意外部履约可靠交付已经完成。

## 当前实际验收和限制

0.4 隔离原生验收：HQ 结构 2→3 升级的 17 项检查通过，保留原 4 个尝试及事件。三个账号的签名 METHODS 在 A（HPOS）、B（CPT）分别注册三个原生方式，其中两个启用且授权全部店铺。

实际中央 HTTP 27 项通过：三个合成原生订单 A133（卡）、A134（钱包）、B133（钱包）使用预期商户、冻结账号/网关；同引用切换账号 409、未知账号拒绝、错误密钥 400。修改卡账号网关/密钥、归档钱包后，旧状态恢复、610px 原生 iframe 收据及冻结旧密钥通知仍可用，新归档创建 403；订单归属和库存分别为 A 的 9/8、B 的 9，重复处理未增加 HTTP 或再次扣库存。另有缓存中的原生渠道不匹配负例 3 项通过。

QA 实际浏览器可添加第四个 Apple Pay 命名草稿（未启用）；Card、PayPal 两个付款选项选择不同原生 ID，并保留电话及原确认项。名称仅用于配置展示，未因此接入官方 Apple Pay/PayPal。原有设置模型 21 项、弹窗事件模型 11 项和单账号故障/域名边界隔离模型 14 项属于隔离模型，不能冒充真实数据库/浏览器或累加为独立功能。归档、未授权或无效账号不会因旧网关 DNS/密钥错误拖停其他健康付款方式。

原本地 HQ 先于店铺安装 0.4，每端 37 个运行文件，旧版 ZIP 在受限私有备份中。原 HQ 已升级结构 3 并迁移默认账号，保留全部原参数、关闭状态、店铺授权和六图标；原店签名 METHODS 只含关闭的默认账号，商户设置只读。未创建原站合成账号/订单、未启用原站收款。旧原站标签有未保存输入，未操作该标签；已另开输出页面。原站实际 390px 浏览器中，页面宽 390px；弹窗 x=12、宽 366、右界 378、底部 832，位于 844px 高视口内且保存按钮可见。已执行打开、读取和取消，未在原站保存。

以上中央支付均用受控 `example.com` 模拟，没有调用真实支付方或输入卡号。0.2/0.3 历史检查点见项目交接，仍保留旧付款兼容证据，不作为当前多账号操作步骤。

支付方早前唯一真实创建请求仍为 `http_request_failed`。公网真实 IPN、字符串引用原样回传、实际收银台/卡验证和正式结算尚未验收。通知没有金额、币种，内部金额按创建时订单汇总，实际结算须对照支付方账单。

完整步骤见源码仓库 [Panapay 部署与验收说明](../../../docs/payments/panapay-deployment.md)。单独插件 ZIP 不含仓库 `docs` 目录，应另取部署文档。历史 0.1 检查点保留在项目交接，不作为当前配置指南。
