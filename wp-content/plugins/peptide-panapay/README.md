# VialCove Panapay 支付

这是可单独安装的 WooCommerce 支付插件。店铺继续使用 WooCommerce 的订单、库存、税费、优惠和原生区块结账；插件只负责创建 Panapay 支付会话、展示支付方收银台，以及验证付款结果通知。卡号和安全码在支付方页面输入，本站不提供收卡表单。

当前对接依据为用户提供的创建支付、浏览器返回和异步通知协议。没有收到查单、退款接口或正式商户资料，因此本插件不提供自动查单、自动退款，也不能据本地测试宣布正式收款已通过。

## 安装与配置

将本目录作为 `wp-content/plugins/peptide-panapay` 安装并启用。插件声明支持原生 Checkout Blocks 和 HPOS，并为 WooCommerce 原生 HPOS、传统 CPT 两种订单存储提供处理路径。第三方替换的订单数据存储不属于当前支持范围；两种原生模式仍需分别做实际验收。

插件头要求 WordPress 6.7、PHP 8.1；服务器需要 OpenSSL 的 AES-256-GCM。当前代码按 WooCommerce 11.2.1 接口核对；隐藏原生电话字段时的条件字段回退需要 WooCommerce 11.2 或更新版本。

配置入口为 **WooCommerce → 设置 → 支付 → Panapay**。新安装默认不启用，测试模式默认开启。每个店铺独立配置：

| 配置 | 作用 |
| --- | --- |
| 网关地址 | 支付方提供的公网 HTTPS 源地址，例如 `https://payments.example.com`；不要填接口路径。 |
| 商户号、签名密钥 | 当前店铺使用的商户凭据。密钥输入框保持空白会沿用已存密钥，不会把旧值显示出来。 |
| 测试模式 | 标识并限制测试商户使用。它不会把正式商户自动变成测试商户。 |
| 标签 | 支付方的可选业务标签。 |
| 请求模式 | 协议的 `1=同步`、`2=异步`，默认 `2`；与测试/正式模式是两个不同设置。 |
| 可信收银台域名 | 网关域名自动纳入。额外域名须向支付方确认后逐个填写精确主机名，不支持通配符。 |

生产 WordPress 环境不能继续测试支付。关闭测试模式后，本站地址也必须是 HTTPS；支付网关与可信收银台始终要求公网 HTTPS。不要修改生产环境标识来绕过这些限制。

服务器可用以下环境变量或同名 PHP 常量提供配置，同名常量优先于环境变量，服务器配置优先于后台保存值：

- `PC_PANAPAY_GATEWAY`
- `PC_PANAPAY_MCHID`
- `PC_PANAPAY_SECRET`
- `PC_PANAPAY_ENCRYPTION_KEY`
- `PC_PANAPAY_DB_HOST`（定制数据库路由时显式指定主库，见下文）

前三项分别对应网关、商户号和签名密钥。`PC_PANAPAY_ENCRYPTION_KEY` 是插件本地加密用的独立 32 字节密钥，使用标准 Base64 编码，不是支付方签名密钥。正式部署应在首次保存支付凭据前确定这项配置。

## 本地与服务器使用同一套流程

浏览器返回地址和服务端通知地址由当前站点的 WooCommerce API 地址动态生成，源码没有写死本机域名或端口。迁到服务器后，正确配置 WordPress HTTPS 地址、反向代理和支付商户参数即可继续使用同一插件。

动态生成只影响新创建的支付会话，已经在支付方创建的旧会话不会自动更换回调地址。迁移存在待付款会话的店铺时，需要保留旧回调入口的连续处理能力，或者先与支付方核对后结束旧会话。

财务占用与落库核对使用独立、自动提交的原生 `wpdb` 连接，不依赖全局 WordPress 连接的外层事务保持提交。原生单库部署使用本站的 `DB_HOST` 和 `DB_NAME`。定制 `wpdb` 路由必须用 `PC_PANAPAY_DB_HOST` 明确指定真实写主库，仍连接同一个 `DB_NAME` 和同一套 schema/表；WooCommerce 订单及支付尝试的读写也必须使用这个主库。这个参数不能让 HyperDB 或任意读写分离方案自动变成已支持配置。

## 怎样认定已经付款

创建支付接口的 `SUCCEEDED` 只表示会话创建成功。支付方返回 `redirect` 时原生结账跳转至收银台；返回 `iframe` 时在受订单访问检查保护的付款页内嵌收银台，并提供打开收银台的链接。

买家回到本站，不会直接把订单标成已付款。插件只在服务端通知通过签名、支付引用、订单状态及已保存订单内容核对后，才申请持久的一次性完成占用，再调用 WooCommerce 原生付款完成流程。重复通知不会获得第二次自动完成机会。

如果执行中断，无法确认原生付款流程是否完成，插件会保留占用并停止自动重复调用。后台显示需要人工核账时，应先在支付方后台核对商户支付引用和交易号；不要删除交易账本、占用或订单支付元数据来强行重试。这项保护约束本站的处理流程，不代表支付方绝不会产生额外扣款。

未来的会员积分、自动履约等业务不能由买家回跳页面触发。对接时应只消费已经过持久已付款核验的原生 WooCommerce 事件/状态，并按订单幂等处理。要在进程或基础设施任意崩溃后仍可靠交付，还需要与持久支付状态一致的 outbox 和幂等消费者；本轮没有实现耐久事件交付、积分或自动履约保障。

## 电话字段与隐私

支付方要求邮箱、电话及账单/收货资料。原生电话字段可用时沿用它；只有商家隐藏原生电话字段时，插件才注册仅在选择 Panapay 时显示并必填的额外电话字段，不自动修改整个店铺的电话设置。条件字段不可用时会给后台提示；缺少必要资料的订单不能发起支付。

创建支付会向已配置的支付方发送订单金额、币种、商品、账单/收货资料、邮箱、电话及协议所需的 IP/浏览器资料。前端支付方式配置只包含标题、说明、测试标记和支持功能，不包含商户密钥或订单隐私。

后台保存的签名密钥、会话 URL 及必要平台交易资料按当前实现加密保存。它不等于把 WooCommerce 所有客户资料都做了数据库加密。密钥、完整收银台 URL、回跳令牌和真实客户资料不得放进 Git、截图交接或普通调试日志。

迁移时必须连同插件交易账本、创建占用表、WooCommerce 数据和原加密依赖一起迁移。当前数据库结构版本为 3，`pc_panapay_creations` 为每个订单保留创建占用；创建中断、超时或结果未知时，不会因临时锁过期自动再次创建远程支付。只有明确失败的尝试可按流程重试，没有强制清除占用的自动入口。配置独立加密密钥时要保留同一密钥；没有配置时，当前实现由 `wp_salt('auth')` 派生密钥，必须保留原 WordPress 认证盐及相关配置。不能只搬数据库、重新生成认证盐后就认为旧付款会话还能继续使用。

## 上线前还要验证

隔离本地 QA、语法检查和签名对照都不能替代公网收款验收。正式网关、商户资质/参数、支持币种和收银台域名仍须由支付方提供并确认。

当前特别待确认：支付方是否接受本插件的字符串商户支付引用，并将请求的 `order_id` 原样返回到通知的 `order_number`；通知协议未提供金额和币种，因此无法独立从通知中复核支付方实际结算金额。

2026-10-31 最新开发验收：隔离 QA 的 HPOS 与 CPT 各通过原生合同 39、故障 24、创建占用 20 个断言；CPT 的结构版本 2→3 升级保留已有记录。两进程通知及创建竞态、HTTP 回调 11 个断言、失败通知空交易号边界 4 个断言、原生 Store API 7 个断言通过。这些是测试断言数，包含两种存储的重复覆盖，不代表同等数量的独立功能。供应商会话响应受控模拟，合成结账订单保持待付款。

隔离 QA 的实际浏览器区块结账已检查：选择 Panapay 时出现所需电话字段，切换银行转账后隐藏，原有确认字段仍保留。未在浏览器点击下单、输入卡号或实际收费。一次合成订单的真实创建请求得到 `http_request_failed`，未取得成功支付会话证据；网关根地址 HEAD 得到 302 不能替代创建接口验收。公网 IPN、字符串引用兼容和正式商户收款仍未验收。

源码仓库中的服务器准备、回调放行、迁移及验收步骤见 [Panapay 部署与验收说明](../../../docs/payments/panapay-deployment.md)。单独安装插件 ZIP 后不包含仓库的 `docs` 目录，请另行取得该部署文档。
